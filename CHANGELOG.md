## [Unreleased]

### Added
- **HEIC Conversion Runs In A Bounded Process Pool (Issue #42)**: HEIC decode + JPEG encode is 97.8% of a run's wall time, per-file independent, and releases the GIL — the textbook `ProcessPoolExecutor` case. The conversion is now split into two phases so this parallelism never touches the tool's correctness invariants. **Phase A (parallel)** maps every HEIC file through a process pool via a new module-level, picklable worker `_convert_heic_worker(heic_path, jpeg_quality, optimize) -> (heic_path, output_path, error)`: each worker builds its own `HeicConverter` and writes the transient `mkstemp` `.jpg` beside the source (issue #26), exactly as the sequential path does; no `self`, no Pillow objects, and no shared state cross the process boundary, and each spawned worker re-imports `src.heic_converter`, which registers the pillow-heif opener (macOS `spawn`). **Phase B (sequential, unchanged)** then walks the results in the *same deterministic scan/category order* a fully sequential run uses, and does all timestamp extraction, collision resolution (`used_timestamps`, the `O_CREAT | O_EXCL` reservation from issue #6), verify-before-delete (issue #7), moving, and original-deletion serially — so the `backup/` tree, which file lands where, and the failure records are byte-for-byte identical to sequential, a property pinned by a same-input parallel-vs-sequential equivalence test. The pool is capped at `min(6, os.cpu_count())` workers, never `os.cpu_count()`: the audit measured returns flattening at 4–6 and *regressing* at 8 because libheif is already internally threaded (~207% CPU sequential), and memory scales at ~0.5 GB/worker, so the cap bounds RSS too. The pool spawns only above a small threshold (8 HEIC files); smaller batches — and every dry run — convert inline on the untouched sequential path, since worker spawn (~65 ms of Pillow/pillow-heif import each) is not amortized for a handful of files. A conversion that fails in a worker is captured and recorded in `failed_files` as `('convert_heic', path, 'HEIC conversion failed')` exactly as before (issue #31 accounting and exit codes unchanged) without aborting the batch; a `BrokenProcessPool` (a worker dying) falls back to sequential conversion for any unfinished files rather than losing them; and `KeyboardInterrupt` cancels outstanding futures and shuts the pool down without orphaning workers. Dry-run parity (issue #10) is preserved — a dry run spawns no pool and reports the same plan. Measured on synthetic 12 MP HEIC fixtures the pool is ~1.76x faster (24 files: 1.88s → 1.07s); the performance audit's real-photo batch went 5m42s → 1m57s on 1,100 files at 4 workers.
- **Packaging Metadata And A Console Entry Point (Issue #15)**: The project now ships a `pyproject.toml` declaring its name, version, description, author, `requires-python = ">=3.8"`, MIT license, and dependencies, so it can be installed with `pip install -e .`. A `[project.scripts]` entry point registers a `tm-monthly-backup` console command (`src.main:main`) that runs the tool from any directory once installed. The existing `src` package is installed as-is via an explicit `[tool.setuptools] packages = ["src"]` list rather than automatic src-layout discovery (which would treat `src/` as a layout root and drop the package name); renaming the package to `tm_monthly_backup` is deliberately left as a separate change since it would touch every import in `src/` and `tests/`.

### Changed
- **Pipeline Orchestration Moved Out Of The Presentation Layer (Issue #13)**: `CLIInterface.process_with_progress` is a presentation object, yet it drove the pipeline — it reached into three *private* `FileProcessor` methods (`_scan_export_directory`, `_delete_sidecar_files`, `_generate_summary`) **and** separately called the public `process_all_files`, which re-scans, re-categorizes, and re-deletes sidecars internally. So scanning, categorization, sidecar deletion, and summary generation each ran **twice** per run (the structure that produced the 1.0.0 duplicate-processing bug), `_generate_summary` was called twice with the first result discarded, and a `progress.update(...)` block was duplicated verbatim. `FileProcessor.process_all_files(dry_run=False, progress=None)` is now the single public entry point for a whole run — scan, categorize, delete sidecars, process, and return the summary — and `CLIInterface` calls only that plus public accessors, reaching into **zero** `_`-prefixed members of `FileProcessor` or its collaborators. Each stage now runs **exactly once** per run. A new, documented `ProgressReporter` seam (in `src/file_processor.py`) lets the presentation layer render and gate a run without owning the loop: `on_no_files()` (scan found nothing), `on_categorized(total, stats) -> bool` (fired once after the single categorization pass with the scanned total and stats; returning `False` aborts the run before any sidecar is deleted or any file is touched — the confirmation seam), and `on_file(path, category, action)` (fired once per processable file as it is handled, never for sidecars). Every hook has a no-op/permissive default, so `progress=None` runs the pipeline headless exactly as before and every existing caller and test is unaffected. `CLIInterface` supplies a `_CLIProgressReporter` that renders the discovery table from the single categorization (no second `batch_categorize`), runs the confirmation prompt, and advances a minimal per-file progress bar — the seam issue #14 will flesh out into real per-phase bars. All observable behavior is preserved: landing paths and collision resolution (#6), verify-before-delete (#7), the parallel HEIC phase (#42), quarantine (#58), unknown routing (#29), dry-run parity (#10), and the exit-code/summary/cancellation semantics (#31). New tests assert scan/categorize/sidecar/summary each run exactly once per confirmed run (they would each be >1 against the old double-invocation), that the reporter fires the total once and once per processable file, and that declining at `on_categorized` aborts before any side effect.
- **HEIC->JPEG Encoding No Longer Pays For `optimize=True` (Issue #40)**: `HeicConverter.convert_heic_to_jpeg` hardcoded `'optimize': True` in the JPEG save kwargs, which tells libjpeg to run a second entropy-coding pass to build optimal Huffman tables. It does not change a single pixel — output is numerically identical, only the coding differs — yet a performance audit measured HEIC conversion at 97.8% of total wall time and this one pass at +71.5 ms per real HEIC (+152% on the encode step, +39% of the whole conversion cost) for only a ~2.3% smaller file. Dropping it makes a HEIC-heavy run **~1.31x faster end to end** (a 100-file / 55-HEIC batch fell from ~16.3s to ~12.6s in the audit) in exchange for slightly larger JPEGs — the right trade for an archive tool on a Mac with terabytes of disk. `optimize` is now off by default and promoted to a `HeicConverter(optimize=False)` constructor argument alongside `jpeg_quality`, so byte-for-byte parity with the old output remains one flag away for anyone who wants it. The conversion still produces a valid, dimension- and EXIF-preserving JPEG (`verify_conversion` unchanged and still green). Size trade-off, measured here on a synthetic detail-rich 2000x2000 HEIC (gradient + per-pixel noise, a proxy that overstates the delta versus the audit's real-photo 2.3% because random noise gives the Huffman optimizer more to squeeze): output grew **+5.15%** (2,242,405 -> 2,357,939 bytes) with optimize off. A new test pins the default to `optimize=False` at the `Image.save` boundary while still asserting the produced JPEG verifies, so a default that quietly turned optimization back on would fail.
- **Dependencies Carry Upper Bounds (Issue #15)**: Every dependency was previously a floor with no ceiling (`pillow>=10.0.0`), so a future major release — Pillow in particular has changed its EXIF APIs across majors — would be accepted silently. Each dependency now pins a conservative upper bound at the next major above the range known to work (`click>=8.0.0,<9`, `pillow>=10.0.0,<12`, `pillow-heif>=0.10.0,<1`, `python-dateutil>=2.8.0,<3`, `rich>=13.0.0,<15`, `hachoir>=3.1.0,<4`). `pyproject.toml` is the single source of truth for the dependency list; `requirements.txt` is retained as a thin, mirrored pointer for the older `pip install -r requirements.txt` workflow.
- **`main.py` Import Simplified (Issue #15)**: Removed the `sys.path.insert` manipulation and the dual `try/except ImportError` fallback from `main.py`, which existed to support a `python src/main.py` invocation that never actually worked (the rest of `src/` uses `from src.…` imports with no installed package). A single clean `from src.cli_interface import …` remains; `python -m src.main` and the installed `tm-monthly-backup` console command are the supported invocations.

### Fixed
- **PNG AI/C2PA Detection No Longer Forces A Full Pixel Decode (Issue #44)**: `FileCategorizer._png_text_has_ai_provenance` probed a PNG's text chunks via `img.text`, and Pillow's `PngImageFile.text` property calls `self.load()` before it will return anything, because tEXt/iTXt chunks are legally permitted to appear *after* IDAT and Pillow refuses to report a partial answer — so merely checking whether a PNG carries AI/C2PA markers silently decoded the entire image into a bitmap, at the same cost as an explicit `load()`, purely to read metadata that in practice every mainstream tool writes before IDAT. A performance audit measured the `.text` probe at 29.29 ms per real PNG (1.2–8.4 MB, best-of-3), statistically identical to a full `load()` at 29.15 ms, versus `im.info` — a plain dict Pillow already populates while parsing the chunk stream during `Image.open()` — at 0.05 ms for the same chunks, roughly 585x cheaper; on the audit's own export this cost 249 ms of a ~53s run (0.5%), and would have scaled to ~1.9s once issue #22 widens AI detection to every PNG rather than just non-screenshots. `_png_text_has_ai_provenance` now reads `img.info` instead of `img.text`, measured on a synthetic 2000x2000 noise PNG carrying a real `tEXt` marker and `eXIf` chunk to show the `_is_generated_content` body dropping from 28.47 ms to 0.03 ms (confirmed against the pre-fix code the same way). Because `img.info` — unlike `img.text` — also carries every *non*-text PNG ancillary chunk Pillow parses before IDAT (`icc_profile` and raw `exif` land there as `bytes`, never as `str`, along with `transparency`/`dpi`/`gamma`/`aspect`), the scan only considers entries whose value is a `str` (`PIL.PngImagePlugin.iTXt` is itself a `str` subclass, so unicode iTXt values are still included) before running the marker search, so a binary chunk can never widen the match surface the way naively stringifying every `info` value would — this keeps the change a how-we-read change, not a what-we-match change. The trade-off is a text chunk written strictly *after* IDAT would now be invisible to this check; no mainstream generator does that — C2PA manifests and generator `Software`/`parameters` chunks are written in the header — so detection is unaffected in practice, and the #8 precision rules this function enforces (provenance matched against identifiable text-chunk **keys** `c2pa`/`parameters`, values matched only at **word boundaries** against the curated marker set, UUID stems validated by `uuid.UUID(...)`) are preserved exactly and unmodified; every existing categorization test still passes untouched, and five new tests assert directly against Pillow's real decode boundary (`Image.tile`, which `load()` empties and nothing else does) that probing a PNG's provenance — whether it matches, matches on a bare key, matches nothing, or coexists with binary ICC-profile/EXIF chunks (including one deliberately carrying a marker word in its byte representation) — never empties it and never mistakes a binary chunk's bytes for text provenance.
- **Dry Run Now Predicts Exactly What A Real Run Does**: `--dry-run` is the only safety mechanism a user has before this tool irreversibly renames, moves, and deletes their photo library, so it must report the *exact* plan a real run would execute — yet the HEIC branch of `FileProcessor._process_single_file` reported the wrong destination for the file type the tool converts most often. In dry-run mode the converted-JPEG path was computed into a local (`Path(file_path).with_suffix('.jpg')`) that was **discarded** — `current_path` was reassigned only on the real-run branch — so `file_extension = Path(current_path).suffix` still yielded `.heic`, and the run reported `backup/photos/<timestamp>.heic`: a filename that will never exist, on a file that always lands as `.jpg`. Both modes now derive a single `planned_extension` (`.jpg` for any HEIC, since the converter's output and the timestamp-derived final name make the intermediate name irrelevant), so the dry-run plan carries the same extension a real run produces. The dry run reads the timestamp from the original `.heic`, whose EXIF is identical to the converted JPEG's, so no conversion — and no disk write — is needed to predict the exact landing path. The previously fixed collision seeding (issue #6, dry-run reservations seeded from disk and tracked in memory), quarantine reporting (issue #58), and unknown-file routing (issue #29) already gave the other categories dry/real parity; this closes the last divergence. A new parity test asserts the set of planned `(category, target)` a dry run reports equals what a real run actually lands for a mixed input set — photo, HEIC, screenshot, video, unknown, undecodable, and two colliding timestamps — and that a dry run performs zero `shutil.move`/`shutil.copy2`/`os.remove`/`os.makedirs` calls and materializes no backup tree.
- **Crafted Filenames Can No Longer Abort The Run Or Corrupt Output Through `rich`**: Filenames arrive untrusted — from iCloud, AirDrop, downloads, and manual renames — and flowed straight into `rich` markup contexts via f-strings, where square-bracket text is parsed as styling markup. A name carrying an unmatched closing tag (`photo[/].jpg`) raised `MarkupError`; because `FileCategorizer.categorize_file`'s "Unknown file type" warning runs inside `batch_categorize`, which is **not** wrapped in a `try/except`, that exception propagated to the top-level handler in `main.py` and **aborted the entire run**. A name carrying a *valid* tag (`IMG_[bold red]1234.jpg`) was silently swallowed instead, so the bracketed text vanished from logs and the summary — and the same crash could fire from inside `display_failures` while the tool was already reporting an error. Beyond markup, raw ANSI/control sequences in a filename reached the terminal unfiltered and could reposition the cursor or rewrite already-printed output. Untrusted values are now neutralized at every boundary: a new `sanitize_for_display` strips ANSI escape and C0/C1 control sequences (leaving ordinary text, brackets included, intact), and `safe_markup` layers `rich.markup.escape` on top for the markup-parsed contexts. `Console.print` f-strings (`check_directories`) and `Table.add_row` cells (`display_failures`) now pass through `safe_markup`; the literal `Text.append` rows in `display_missing_exif_warning`, which never parse markup, are stripped of control sequences without escaping (which would corrupt them). The logging path is closed at a single boundary: `RichHandler` is configured with `markup=False` — the tool never emits intentional markup through the logger, so disabling it costs nothing — and a `_SanitizingLogFilter` collapses each record to its final text and removes control sequences, so no log message can drive the terminal regardless of how a call site formats. Log call sites carrying untrusted filenames across `file_processor.py`, `file_categorizer.py`, `heic_converter.py`, and `exif_handler.py` were additionally converted from f-strings to lazy `%s` formatting, keeping the untrusted value a parameter rather than part of the format string. A `photo[/].jpg`-style path now processes end to end without raising and appears literally in the summary; a `[bold red]` name is preserved verbatim; ANSI sequences are stripped from all output.
- **Symlinks Archive The Photo They Point At, Not The Link Itself**: A symlink in `export/` pointing at a real image is intentionally kept by the scan (issue #54's `os.path.isfile` follows the link and sees a regular file), but `FileProcessor._process_single_file` then filed it with `shutil.move`, which falls through to `os.rename` on a same-filesystem move — relocating the **symlink itself**. `backup/photos/<timestamp>.jpg` became a symlink pointing back at the original target rather than a copy of the photo, so the archive held a hollow pointer: the run reported success and the file appeared in every listing, but `open()` failed the moment the user tidied the target away (emptied a scratch folder, unplugged the drive it lived on). The failure was even filesystem-dependent — a *cross*-filesystem `shutil.move` copies real bytes instead, so the same input produced a photo or a dead link depending only on where `backup/` sat. Placement now goes through `_place_source_content`, which detects a symlink (`os.path.islink`) and **copies the resolved target's real bytes** onto the reserved destination (`shutil.copy2` of `os.path.realpath(path)`, mirroring the target's mtime), then removes **only the link** from `export/` (`os.remove` on a symlink unlinks the link, never its target). The archived entry is always a regular file carrying the photo's bytes, identical whether `backup/` is on the same volume or another, and it survives the target being deleted afterward. Crucially the target — which a symlink can place entirely **outside** `export/` — is never moved, deleted, or modified; only the link is removed. The same copy-then-unlink applies on every path a symlinked source can take: HEIC targets still convert to a real JPEG (the original-delete step unlinks the link, sparing the target HEIC), undecodable targets quarantine a real **copy** into `backup/corrupt/` under the link's name, and unrecognized targets file a real copy into `backup/unknown/`. A plain regular file is still moved, so `export/` is fully drained as before. The destination-collision safety (issue #6), verify-before-delete for HEIC (issue #7), and lazy-directory guarantees are all preserved.
- **Non-Regular Files No Longer Hang The Run**: `FileProcessor._scan_export_directory` appended every non-hidden entry `os.walk` yielded without checking it was a *regular* file. `os.walk` excludes directories, but its `filenames` list still surfaces FIFOs (named pipes), sockets, and device nodes — non-regular files an untrusted `tar`/`cpio` archive materializes when extracted into `export/`, which is precisely this tool's threat model (a hostile *file*, not a hostile user). Opening a FIFO for reading **blocks until a writer appears**, and there is no writer, so a later `Image.open(...).load()` (the undecodable-file gate, or an EXIF read) stalled the entire run **forever** — `--dry-run` included, since categorization runs before the dry-run branch — with only a never-advancing spinner and the photo beside it never backed up. The scan now rejects any entry that is not a regular file with `os.path.isfile(path)`, a `stat`-based check that **never opens the file** (so the check itself cannot block) and returns `True` only for regular files and symlinks whose target is a regular file. FIFOs, sockets, device nodes, and broken symlinks are skipped and logged; a symlink pointing at a real image is still kept for normal processing. The existing hidden-file skip and hidden-directory pruning are unchanged.
- **Hidden Directories Are No Longer Walked, Archived, Or Deleted From**: `FileProcessor._scan_export_directory` skipped hidden *files* (`filename.startswith('.')`) but never pruned hidden *directories*, so `os.walk` descended straight into every dot-directory under the export root — the macOS system trees (`.Trashes`, `.Spotlight-V100`, `.fseventsd`, `.DocumentRevisions-V100`) and a repo drop-off's `.git`. Any non-hidden file inside one became a full pipeline participant: `.Trashes/deleted.jpg` (a photo the user deliberately threw away) was resurrected into `backup/photos/` under a fabricated timestamp, `.git/objects/pack/x.jpg` was archived as a photograph, and — worst — an `.aae` sidecar found inside a hidden tree was **permanently deleted** by `_delete_sidecar_files`, which runs first and does not care where a file came from. On a macOS export volume these directories are ubiquitous, files are *moved* (mutating the source trees), and the `.aae` deletion is irreversible. The scan now prunes hidden directories in place during the walk (`dirs[:] = [d for d in dirs if not d.startswith('.')]`), the documented `os.walk` mechanism for skipping subtrees, so a hidden directory at *any* depth is never descended into, its contents are never categorized, archived, or discovered for sidecar deletion, and it is left exactly as found in `export/`. The existing leaf-level hidden-file skip is retained, and normal (non-hidden) subdirectories are still walked and their photos processed.
- **Undecodable Files Are Quarantined, Not Archived As Photos**: `FileProcessor._process_single_file` never established that a file carrying a photo extension was decodable media. It asked `ExifHandler.extract_timestamp` (which returns `None` on any failure), fell back to filesystem mtime, then renamed and moved — so a zero-byte `empty.jpg`, a text file named `.png`, or a JPEG truncated by an interrupted iCloud/AirDrop download was renamed to a fabricated timestamp and filed into `backup/photos/` as if it were a photograph. The rename is the damage: `empty.jpg` at least announced itself, but `2026.08.01.12.00.44.jpg` is indistinguishable from a real photo in a directory of thousands, and the archive is the only copy. Image-typed files (`PHOTO`/`SCREENSHOT`/`GENERATED`) whose extension Pillow can decode (`.jpg`/`.jpeg`/`.png`/`.gif`/`.tiff`/`.tif`/`.bmp`/`.webp`) are now decode-verified before the rename: `Image.open(path).load()` forces a full pixel decode, which — unlike the lazier `Image.verify()` — actually catches a JPEG truncated to half its bytes (`verify()` validates structure but never reads the pixel data, so it passes a truncated JPEG); a zero-byte file is rejected up front. Files that fail are moved to `backup/corrupt/` under their **original filename** (a corrupt file has no reliable capture time, so its name is the only clue for recovery), never overwriting a name already there (`name (1).ext` disambiguation, reusing the atomic `O_CREAT | O_EXCL` reservation from issue #29), with the directory created lazily so it is never an empty phantom. RAW formats (`.dng`/`.cr2`/`.nef`/…) are deliberately excluded from the gate — Pillow cannot decode them, so a valid RAW would be falsely quarantined — and HEIC/HEIF are left to their existing conversion-verification path (issue #7). Quarantined files are reported as a distinct outcome — counted in a new `files_quarantined` tally, neither a clean "processed" nor a tool "failure" — and the results banner no longer reads an unqualified "Success!" when files were quarantined; `--dry-run` reports the same quarantine decisions a real run would make without moving anything. Exactly one full decode is performed per file (the downstream EXIF read only touches the header), so no file is decoded twice.
- **AI-Content Detection No Longer Misfiles Ordinary Photos**: `FileCategorizer._is_generated_content` scanned every PNG text chunk for the bare substrings `['gpt', 'chatgpt', 'openai', 'c2pa', 'ai', 'generated']`. Because `'ai'` was matched with `in` against the whole lowercased value, it hit inside ordinary English words — ch**ai**r, tr**ai**l, po**rtrai**t, det**ai**l, r**ai**n, Sp**ai**n — so a real photo captioned "Portrait of a chair on a trail" was categorized `GENERATED` and routed into `backup/generated/`, where a manual cleanup could delete it unnoticed; `'generated'` matched captions just as broadly. Detection is now precise: provenance is matched against identifiable PNG text-chunk **keys** (`c2pa`, `parameters` — the Stable Diffusion / AUTOMATIC1111 key), and values are matched only at **word boundaries** against a curated marker set (`chatgpt`, `openai`, `gpt-4`/`gpt-4o`, `dall-e`/`dall·e`, `midjourney`, `stable diffusion`, `firefly`, `c2pa`). The bare `'ai'` and `'generated'` tokens are dropped entirely. UUID-style filenames are now validated by parsing the stem with `uuid.UUID(...)` inside `try/except ValueError` instead of the shape-only `len == 36 and four hyphens` check, which accepted any 36-character name with four hyphens regardless of its hex digits. The editing-software heuristic (editing `Software` present with no original capture timestamp) now reads `DateTimeOriginal`/`DateTimeDigitized` from the Exif **sub-IFD** as well as IFD0 (issue #25): reading only IFD0 never found the sub-IFD capture time, silently collapsing the intended "edited AND no capture time" rule into "any edited image" and misfiling genuinely edited photos that had kept their timestamp. Genuine AI/C2PA content is still caught; ordinary photos carrying those words in a caption are not.
- **Videos Named From Their True Local Capture Time, Not UTC**: `ExifHandler._extract_video_timestamp` named MOV/MP4 files from hachoir's `mvhd` creation_time, which QuickTime defines as **UTC**. Apple, however, records the real local wall-clock capture time — with its UTC offset — in the `com.apple.quicktime.creationdate` metadata key, and the tool never read it. Every video shot after roughly 8pm Eastern therefore rolled forward a calendar day: a clip shot 2026-07-04 21:33 EDT was stored as `2024.06.16.01.33.03.MOV`, filed under July 5th when it was shot on the 4th, with the original filename destroyed and no manifest to recover it. The extractor now prefers `com.apple.quicktime.creationdate`, parsing the offset-bearing ISO-8601 string and keeping the **local wall-clock reading** (`21:33:03` stays `21:33:03`) so a video and a photo captured at the same instant share the same `YYYY.MM.DD.HH.MM.SS` stem. hachoir does not surface this key, so the value is read directly from the QuickTime/MP4 box structure (`moov` → `meta` → `keys`/`ilst`), handling both the QuickTime and ISO `meta` layouts and skipping large boxes without loading them. The hachoir/`mvhd` UTC path remains only as a fallback for containers that lack the Apple key; that fallback can still be off by the UTC offset — a pre-existing limitation this change does not worsen. Image/EXIF timestamp handling is untouched.
- **Unrecognized Files Are Now Actually Filed (No Silent Leave, No Phantom Directory)**: `FileCategory.UNKNOWN` was categorized, counted, rendered against `backup/unknown/` in the results table, and its directory was even pre-created — but `get_processable_files` omitted it from the processable set, so `process_all_files` never moved an unknown file. Unrecognized files were silently left in `export/` while `backup/unknown/` sat empty forever, yet the summary counted them and the exit code implied a clean, fully drained run — exactly the mismatch that made the documented cleanup step destructive. Unknown files are now genuinely routed into `backup/unknown/`. Because they carry no metadata to derive a timestamp from, they keep their **original filename** rather than being renamed to a fabricated timestamp that would erase the one identifying detail available for manual review. A name already present there is preserved by disambiguating the incoming file as `name (1).ext`, `name (2).ext`, … using the same atomic `os.open(..., O_CREAT | O_EXCL)` reservation the timestamped path uses, so an unknown file never overwrites one a prior run filed. The directory is created lazily, only when a file actually lands in it, so `backup/unknown/` is never an empty phantom. `get_processable_files` now derives its categories from the `FileCategory` enum (everything except sidecar) instead of a hand-maintained list, so a newly added category can never again be silently dropped. `ensure_target_directories` no longer eagerly creates `backup/unknown/`. Docs (`README.md`, `docs/cli-usage.md`, `docs/troubleshooting.md`) already described this destination and now match the code.
- **Every Failure Is Now Accounted For (No Silent Success)**: When `HeicConverter.convert_heic_to_jpeg` returned `None` (a failed conversion), `FileProcessor._process_single_file` `return`ed without recording anything, so the unconvertible `.heic` was silently dropped: it was left in `export/`, `files_failed` stayed `0`, the summary printed "Processing Complete - Success!", and the process exited `0` for a run that had not processed the file. The returns-`None` branch now records `('convert_heic', path, 'HEIC conversion failed')` in `failed_files`, so the file counts toward `files_failed`, appears in the failure table, retitles the summary to "With Errors", and drives a non-zero exit. Every discovered processable file now lands in exactly one bucket — processed or failed — a `files_processed + files_failed == files_seen` invariant asserted in the test suite.
- **Exit Codes Have Distinct, Documented Meanings**: `main.py` exited `1` for both partial per-file failures *and* fatal precondition errors (missing/unwritable/overlapping directories, unexpected exceptions), and a cancelled run was indistinguishable from a clean success because `process_with_progress` signalled "cancelled" and "no files" with an empty dict inferred from falsiness. The exit path now uses an explicit, testable taxonomy (`determine_exit_code`): `0` = every discovered file processed with zero failures; `1` = processing ran but one or more files failed; `2` = precondition failure (missing/unwritable directory, the export/backup overlap rejection, or an unexpected error — nothing was processed); `130` = cancelled by the user (declined prompt or `SIGINT`, per the POSIX `128 + signal` convention). `process_with_progress` now returns a status-tagged result instead of an empty dict, so a declined confirmation can never be reported as success. The exit-code table in `docs/cli-usage.md`, which previously listed `1` twice with conflicting meanings, is updated to match.
- **Backup Files No Longer Overwritten Across Runs**: `FileProcessor` judged filename collisions with `used_timestamps`, an in-memory `set` populated only during the current process and never seeded from what already sat in `backup/`. Because `shutil.move` overwrites its destination silently, two photos processed in *different runs* (e.g. two monthly dumps) that resolved to the same `YYYY.MM.DD.HH.MM.SS` name caused the second run to overwrite — and irrecoverably destroy — the first run's file, while reporting a clean summary and exiting `0`. An attacker who could influence a filename in `export/` could even *aim* the overwrite at a known archive name. Collision detection is now filesystem-authoritative and scoped per target directory: before a file is filed, its destination path is reserved atomically with `os.open(..., O_CREAT | O_EXCL)`, which closes the check-then-move TOCTOU window and can never select an already-present file as the move target. The timestamp is bumped a second at a time until a free path is claimed, and the real file is then moved onto the empty placeholder the reservation created (a failed move drops the placeholder). Each per-directory name set is seeded once from the directory's on-disk contents so resolution does not rediscover conflicts one filesystem probe at a time. A dry run stays side-effect free but now reports the *bumped* path a file would take when its natural name is already occupied, instead of a name a real run would overwrite.
- **Cross-Category Timestamp Collisions Eliminated**: `used_timestamps` was a single flat set shared across every category, so a photo and a video (or screenshot) resolving to the same second were treated as a collision and one was bumped by a second — even though they are written to *separate* directories and can never collide on disk. The resulting filename no longer matched the media's true capture time. Collision tracking is now keyed by target directory (`Dict[str, Set[str]]`), so files in different category directories share no collision namespace and each keeps its exact timestamp; two files in the *same* directory still bump correctly.
- **HEIC Original Verified Before Deletion**: `FileProcessor._process_single_file` deleted the original `.heic` with `os.remove` the instant `convert_heic_to_jpeg` returned a non-`None` path, with no check that the JPEG was actually valid on disk. Because the converter returns its output path immediately after `image.save` without inspecting the result, a truncated write, a zero-byte file, a full disk, or a partial decode all produced a "successful" return — after which the only copy of the original photo was destroyed. The pipeline now calls `HeicConverter.verify_conversion` against the *actual* converted path (the unique `mkstemp` name, not a stale `{stem}.jpg`) before the original becomes eligible for deletion: the JPEG must exist, decode, match the source dimensions, and preserve EXIF. On verification failure the original `.heic` is left in place in `export/`, the unverifiable artifact is removed, and the failure is recorded in `failed_files` so it drives a non-zero `files_failed`. The delete is further deferred until *after* the verified JPEG has landed in `backup/photos/<timestamp>.jpg`, so a failure during the move can never leave the user with neither the original nor a filed copy. Deletion now routes through the single `HeicConverter.cleanup_original_heic` implementation, retiring the inline `os.remove` duplicate; `cleanup_original_heic` was also repaired to verify against an explicit converted path rather than the stale `{stem}.jpg` name.
- **HEIC Conversion No Longer Overwrites Existing Files**: `HeicConverter.convert_heic_to_jpeg` wrote the converted JPEG to a fixed `{stem}.jpg` beside the HEIC. When a real sibling with that name already sat in the export tree — an exact `IMG_1234.jpg`, or an uppercase `IMG_1234.JPG` on a case-insensitive APFS volume — the conversion silently overwrote and destroyed that photo, reporting `files_failed: 0` with no error. Because `os.walk` returns APFS entries in hash order, the loss occurred on roughly half of all same-stem pairs. The converter now reserves a guaranteed-unique output path with `tempfile.mkstemp` (atomic `O_CREAT | O_EXCL`) on the same filesystem, so it can never collide with an existing sibling in either the exact-name or case-insensitive case, and the downstream `shutil.move` to `backup/photos/<timestamp>.jpg` stays a cheap same-volume rename. Callers already use the returned path, so the transient intermediate name is invisible to the final timestamp-derived backup filename.
- **Overlapping Export/Backup Directories Rejected**: The tool now refuses to run when `--export-dir` and `--backup-dir` overlap — the same directory, or one nested inside the other. Because the export tree is consumed in place (sidecars and converted-from HEIC originals are deleted), an overlapping destination let a run re-ingest and destroy its own archive. Paths are resolved with `Path.resolve()` (normalizing symlinked and relative aliases) and compared for equality and containment in both directions. The guard runs on both entry surfaces: `CLIInterface.check_directories` reports the conflict and exits non-zero, and `FileProcessor.process_all_files` raises `ValueError` before scanning so a programmatic caller cannot bypass it.
- **Timestamp Rollover Crash**: `ExifHandler.handle_duplicate_timestamp` no longer raises `ValueError` when incrementing past a second, minute, hour, or month boundary. Replaced the manual `datetime.replace` arithmetic with `timedelta`, which handles all rollovers correctly.
- **EXIF Sub-IFD Timestamp Reachability**: `ExifHandler.extract_timestamp` now reads the Exif sub-IFD (pointer tag `0x8769`) via `Image.Exif.get_ifd`, merging it with IFD0 before the priority walk. `DateTimeOriginal` (0x9003) and `DateTimeDigitized` (0x9004) live in the sub-IFD, which `Image.getexif()` does not expose at the top level, so every photo was previously named from IFD0 `DateTime` (file modification time) instead of capture time. The declared priority `DateTimeOriginal` > `DateTime` > `DateTimeDigitized` is now actually honored, and a malformed higher-priority tag falls through to the next candidate rather than aborting. Applies to HEIC as well, since pillow-heif exposes EXIF through the same API.

### Tests
- **Interruption And Partial-Failure Behavior Pinned (Issue #46)**: `FileProcessor` deletes originals, so how a run behaves when it is cut short is as load-bearing as the happy path — yet the most important piece was unasserted. `_process_category` catches `except Exception`, and because `KeyboardInterrupt` is a `BaseException` (not an `Exception`), a Ctrl-C raised mid-batch escapes the per-file loop and unwinds the run instead of being swallowed into a per-file skip that would grind through the entire library while the user holds the key. A new `tests/test_interruption.py` pins that contract: a `KeyboardInterrupt` on the third file propagates out of `process_all_files` (`assertRaises`), the two files processed before it already landed in `backup/`, the remaining three are untouched in `export/`, and the interrupt is never demoted to a recorded failure — a test that fails the instant that `except Exception` is "cleaned up" to a bare `except:`/`except BaseException`. The module also pins two previously unasserted partial-failure behaviors: a full disk (`OSError(ENOSPC)`) does not abort the batch — every remaining file is still attempted and recorded as a `move_file` failure while the run completes — and a file deleted between the scan and processing is absorbed by `batch_categorize` so the run finishes over the survivors without crashing. Scenarios already covered elsewhere (one-file `PermissionError` partial failure, `clear_processing_state` fully resetting, and the top-level `main.py` `KeyboardInterrupt` handling) are deliberately not duplicated.
