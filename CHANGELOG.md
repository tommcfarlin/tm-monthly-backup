# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Fixed

- The Apple-sidecar deletion gate now also holds when the scan skipped a file
  for an unexpected (non-junk) reason. Previously an `export/` holding a real
  photo under a dotted name plus its valid `.aae` deleted the edit history of
  a photo that was never archived; the kept candidates are reported with a
  new "unexpectedly left behind" reason. A junk-only skip (`.DS_Store`,
  `.localized`, `Thumbs.db`) still does not block sidecar cleanup, and an
  all-sidecar export still deletes its sidecars.
- Transient converted JPEGs are now swept on every exit from the processing
  phases, including Ctrl-C, and pool-produced outputs are tracked the moment
  their paths arrive (including after a broken pool). Previously an interrupt
  could leave a converted JPEG in `export/` for the next run to re-ingest as
  a duplicate or a false "corrupt" quarantine. One narrow leak remains and is
  now documented instead of overclaimed: a pool worker that dies after
  writing its JPEG but before returning its path.
- The exit-1 closing line now names the actual reason(s) -- failures,
  quarantined files, kept sidecars, an unexpectedly skipped file, or an
  unverified landing -- instead of always printing the failure count, which
  announced "Completed with 0 failures." for a quarantine-only run. The exit
  code documentation in `docs/cli-usage.md` now matches what exits `1`.

## [1.3.0] - 2026-08-07

Milestones 1.1.0, 1.2.0 and 1.3.0 all ship here: 1.0.0 was the last tagged
release, and no 1.1.0 or 1.2.0 release was ever cut, so everything below
accumulated on top of 1.0.0. 68 issues closed.

### Upgrading from 1.0.0 -- read this first

**One behavior change can break an existing unattended run.** A non-interactive
invocation (no terminal attached -- cron, a pipe, CI) now **requires
`--yes`**. Without it the run refuses immediately with an actionable message
and exits `2`, rather than hanging forever on a confirmation prompt nobody can
answer, or consuming piped data as the answer. This also means a case that
previously exited `0` can now exit `2`: an `export/` that is non-empty at the
top level but contains nothing the tool can process. If you have a cron entry
or script calling this tool, **add `--yes` to it before upgrading.**

**A second change affects automated callers only: more conditions now exit `1`.**
The exit code previously reflected only per-file failures, which meant a run
could print a warning banner a human would act on and still tell a script it
succeeded. It now matches the banner exactly: a quarantined undecodable file, an
Apple sidecar kept because its delete failed, a real hidden file left in
`export/`, or an archive that failed its own post-run verification all exit `1`
instead of `0`. A clean run still exits `0`, and so does a run whose only skip is
OS junk (`.DS_Store`, `.localized`, `Thumbs.db`) -- every macOS export tree
carries one of those, so it would be useless as a signal. If you have a script
branching on the exit code, it will now correctly stop on cases it previously
sailed past; that is the point, but it is a behavior change.

Two further changes are visible immediately but break nothing:

- **A default run is much quieter.** It now prints warnings, errors and a
  summary rather than one line per file. Anything that is your only trace of a
  destructive or surprising decision -- a skipped non-regular file, a
  quarantined undecodable file, a deleted sidecar, a file routed to
  `backup/unknown/`, a failed HEIC verification, any recorded failure -- is
  still shown. `--verbose` restores the per-file detail.
- **Archived filenames now carry a single canonical extension.** Newly
  processed files land as lowercase, with `.jpeg`/`.tiff`/`.mpeg` collapsed to
  `.jpg`/`.tif`/`.mpg`. Files already in `backup/` keep the names they have;
  nothing is renamed retroactively.

And one default worth knowing about: **HEIC conversion quality is now 98**, up
from 95. The original HEIC is still deleted after a verified conversion, so the
archived JPEG is the only surviving copy -- 98 roughly halves the per-channel
quantization error for about a third more disk. `--jpeg-quality` still accepts
anything from 1 to 100.


### Added
- **HEIC Conversion Runs In A Bounded Process Pool (Issue #42)**: HEIC decode + JPEG encode is 97.8% of a run's wall time, per-file independent, and releases the GIL — the textbook `ProcessPoolExecutor` case. The conversion is now split into two phases so this parallelism never touches the tool's correctness invariants. **Phase A (parallel)** maps every HEIC file through a process pool via a new module-level, picklable worker `_convert_heic_worker(heic_path, jpeg_quality, optimize) -> (heic_path, output_path, error)`: each worker builds its own `HeicConverter` and writes the transient `mkstemp` `.jpg` beside the source (issue #26), exactly as the sequential path does; no `self`, no Pillow objects, and no shared state cross the process boundary, and each spawned worker re-imports `src.heic_converter`, which registers the pillow-heif opener (macOS `spawn`). **Phase B (sequential, unchanged)** then walks the results in the *same deterministic scan/category order* a fully sequential run uses, and does all timestamp extraction, collision resolution (`used_timestamps`, the `O_CREAT | O_EXCL` reservation from issue #6), verify-before-delete (issue #7), moving, and original-deletion serially — so the `backup/` tree, which file lands where, and the failure records are byte-for-byte identical to sequential, a property pinned by a same-input parallel-vs-sequential equivalence test. The pool is capped at `min(6, os.cpu_count())` workers, never `os.cpu_count()`: the audit measured returns flattening at 4–6 and *regressing* at 8 because libheif is already internally threaded (~207% CPU sequential), and memory scales at ~0.5 GB/worker, so the cap bounds RSS too. The pool spawns only above a small threshold (8 HEIC files); smaller batches — and every dry run — convert inline on the untouched sequential path, since worker spawn (~65 ms of Pillow/pillow-heif import each) is not amortized for a handful of files. A conversion that fails in a worker is captured and recorded in `failed_files` as `('convert_heic', path, 'HEIC conversion failed')` exactly as before (issue #31 accounting and exit codes unchanged) without aborting the batch; a `BrokenProcessPool` (a worker dying) falls back to sequential conversion for any unfinished files rather than losing them; and `KeyboardInterrupt` cancels outstanding futures and shuts the pool down without orphaning workers. Dry-run parity (issue #10) is preserved — a dry run spawns no pool and reports the same plan. Measured on synthetic 12 MP HEIC fixtures the pool is ~1.76x faster (24 files: 1.88s → 1.07s); the performance audit's real-photo batch went 5m42s → 1m57s on 1,100 files at 4 workers.
- **Packaging Metadata And A Console Entry Point (Issue #15)**: The project now ships a `pyproject.toml` declaring its name, version, description, author, `requires-python = ">=3.8"`, MIT license, and dependencies, so it can be installed with `pip install -e .`. A `[project.scripts]` entry point registers a `tm-monthly-backup` console command (`src.main:main`) that runs the tool from any directory once installed. The existing `src` package is installed as-is via an explicit `[tool.setuptools] packages = ["src"]` list rather than automatic src-layout discovery (which would treat `src/` as a layout root and drop the package name); renaming the package to `tm_monthly_backup` is deliberately left as a separate change since it would touch every import in `src/` and `tests/`.
- **A `--yes`/`-y` Flag For Non-Interactive Invocation (Issue #33)**: `CLIInterface` called `rich.prompt.Confirm.ask` unconditionally at two points — the empty-`export/` "Continue anyway?" prompt in `check_directories`, and the "Proceed with processing N files?" prompt every real run hit inside the confirmation seam issue #13 introduced. `Confirm.ask` routes to Python's builtin `input()`, which raises a bare `EOFError` the instant it is reached with no TTY attached — cron, CI, a systemd unit, `nohup`, or any piped invocation — so the exact automation workflow the docs recommended (a monthly cron job) failed every run, having processed nothing, with the two prompts failing in different, equally unhelpful ways depending on which one it hit first (`click`'s bare `Aborted!` for the empty-export path, since it sits outside `main.py`'s `try`; `Unexpected error: EOF when reading a line` for the other, since `except Exception` caught a perfectly ordinary, entirely predictable condition and reported it as an internal fault). A new `--yes`/`-y` flag is the explicit opt-out: `CLIInterface.check_directories(auto_confirm=...)` and `CLIInterface.process_with_progress(yes=...)` now thread the flag down to `_CLIProgressReporter.on_categorized`, the single confirmation seam issue #13 established, where `Confirm.ask` is skipped entirely (never called, not stubbed to auto-answer) when `--yes` was passed — so a `--yes` run is a real, unattended pipeline execution, not a mocked one. `main.py` also detects the no-terminal case directly (`sys.stdin.isatty()`, factored into a small `_stdin_is_interactive()` so it can be exercised in tests without a real TTY) and fails fast with `click.UsageError("No terminal available for confirmation. Re-run with --yes or --dry-run.")` — a one-line, actionable instruction in place of the stack-trace-shaped failure — before logging, directory checks, or any other setup runs. `--dry-run` was already exempt from the "Proceed" prompt (it makes no change to confirm), but the empty-export prompt in `check_directories` still blocked it for no reason; both `--yes` and `--dry-run` now independently skip it, so `--dry-run` alone is safe to pipe unconditionally, matching the issue's requirement that a dry run never prompt. None of the existing exit-code taxonomy (issue #31) shifted in the process: a `--yes`-confirmed run that actually fails still exits `1`, a clean `--yes` run still exits `0`, and declining the prompt without `--yes` still exits `130` — the flag changes only whether the run is asked, never what its outcome earns. `docs/cli-usage.md` gained a `--yes` row in the options table and a new Non-Interactive / Automated Use section with a corrected cron recipe that passes `--yes`; `README.md` gained a matching Features bullet and usage example. New tests cover the full contract without ever patching `Confirm.ask` for the `--yes` path: `--yes` proceeds and files a real photo while asserting `Confirm.ask` is never called; the same for the empty-export prompt; a non-`--yes` run still calls `Confirm.ask` and declining it aborts before the sidecar is deleted or any file moves, tagging the result `cancelled`; a `--yes` run through `main` with an injected per-file failure still exits `1`, not `0`; a non-interactive invocation with neither `--yes` nor `--dry-run` exits `2` with a message naming both flags and containing neither `EOFError` nor `Unexpected error`; and `--dry-run` completes non-interactively over an empty `export/` with no prompt at all.
- **`--jpeg-quality` Promotes An Existing Tunable To A Real Option (Issue #41)**: `HeicConverter.__init__` had, since issue #40, a thoughtfully-defaulted `jpeg_quality` parameter (and an `optimize` one), but `FileProcessor.__init__` constructed `HeicConverter()` with no arguments at all — there was no path from `main.py` down to it, so the only configurable thing in the entire tool was the pair of directory paths, and `docs/cli-usage.md` had promised a `TM_BACKUP_QUALITY` environment variable and a `~/.tm-monthly-backup.yml` config file that never arrived. The gap is now a real CLI option: `--jpeg-quality` (`click.IntRange(1, 100)`, default `95` at the time, matching `HeicConverter`'s own default — later raised to `98`, see the Changed entry below) reaches the converter's encoder directly. It is bundled into a new frozen `Settings` dataclass (`jpeg_quality`) rather than becoming another scalar parameter on `FileProcessor.__init__` — `FileProcessor(export_dir, backup_dir, settings=Settings(...))`, with `settings` defaulting to `Settings()` so all ~50 existing call sites across the test suite that construct a bare `FileProcessor(export_dir, backup_dir)` are unaffected — and `frozen=True` guarantees no code path can mutate a run's configuration midway through it; `CLIInterface` gained a matching `jpeg_quality` constructor keyword that builds the `Settings` object internally, so `main.py` still deals only in plain scalars, consistent with how `--yes` (issue #33) threads through the same layers. The same setting holds under both HEIC conversion paths issue #42 established: quality reaches the parallel pool for free, since `_convert_heic_files_parallel` already read `self.heic_converter.jpeg_quality`/`.optimize` off the (now settings-constructed) converter before this change. Config-file/env-var configurability was considered and deliberately declined, per the issue's own recommendation: this is a small personal tool, and the promised-but-never-shipped "Environment Variables" / "Configuration File" subsections of `docs/cli-usage.md` are replaced with an honest accounting of the current, closed set of CLI options, plus an explicit note that the heuristic tables (extension sets, screenshot patterns, AI-provenance markers, editing-software list) stay hardcoded on purpose — a false-positive there is a precision bug for issues #8/#22 to fix, not a knob for every user to carry their own copy of the rule. `README.md` and `docs/cli-usage.md` (options table, a new "HEIC Conversion Tuning" example, and the "HEIC Conversion" and "Configuration" sections) are updated to match; the stale "optimize=True" mention issue #40 left behind in prose (the default flipped to `False` in that issue, but the surrounding doc paragraph was not touched) is corrected in the same pass since it sits inside the exact paragraph this issue rewrites. This issue originally also added a `--keep-heic` retention flag alongside `--jpeg-quality`; it was implemented, then withdrawn before release under issue #65 — see that entry below for why.
- **`-h` Registered As A Help Alias (Issue #64)**: `click` registers `--help` on every command automatically but never a `-h` short form, so the docs' earlier claim that `-h` worked (corrected to remove it in issue #18, once the discrepancy was found) had actually been describing a nonexistent option: invoking `tm-monthly-backup -h` raised click's own unknown-option usage error, exit code 2, not help text. `main`'s `@click.command()` now passes `context_settings={"help_option_names": ["-h", "--help"]}`, click's own supported mechanism for adding short aliases to the built-in help option, so `-h` and `--help` are the same eager, click-internal option and produce byte-identical output. Because that option resolves and exits before `main()`'s body ever runs, `-h` is unaffected by the issue #33 no-terminal precondition gate — the first statement in `main()` that exits `2` when no TTY is attached and neither `--yes` nor `--dry-run` was passed — so `-h` in a pipe or a cron job still prints help and exits `0` rather than being misrouted into that gate's "No terminal available" message; this was verified directly by invoking `-h` with stdin redirected from `/dev/null`. No short flag collision existed to resolve: the command's only other short options are `-y` (`--yes`, issue #33) and `-v` (`--verbose`), neither of which is `-h`. New tests assert `-h` exits `0` and prints the same help text `--help` does (both under `click.testing.CliRunner`, which never presents stdin as a tty, so the assertion doubles as no-terminal coverage), that neither invocation's output contains the no-terminal message, and pin the two outputs as exactly equal; the existing test that pins `--yes`'s presence in `--help`'s output is untouched and still passes unchanged.

### Changed
- **`FileProcessor` Takes A Single `Settings` Argument (Issue #67)**: issue #41 bundled the HEIC tunables into a frozen `Settings` record but left the directories as positional parameters, so the constructor carried two configuration channels and the immutability guarantee was only partial -- `jpeg_quality` could not change mid-run, but `export_dir`/`backup_dir` were plain mutable attributes, meaning a run could be silently repointed at a different directory partway through. `Settings` now holds the directories too, `FileProcessor.__init__` takes `settings` as its one parameter, and `export_dir`/`backup_dir` are read-only properties so the immutability claim is enforced rather than described. No backward-compatible two-positional form was kept: it would have preserved exactly the mixed shape the change exists to remove. All 101 call sites updated (100 in tests, 1 internal), with a paren-aware transformer rather than a regex, since several nest a comma inside `os.path.join(...)` and five span multiple lines. Zero behavior change.
- **Default HEIC->JPEG Quality Raised From 95 To 98**: the tool converts every HEIC to JPEG and then **deletes the original** after a verified conversion (issue #7), so the archived JPEG is the only surviving copy of that photograph — which makes the encode quality a one-way decision rather than a tunable preference. JPEG has no lossless mode, so some quantization loss is unavoidable, but the default was set at 95 before anyone measured what it costs. Measured across real HEIC exports from an iPhone 15 Pro (mean absolute per-channel error against the decoded source, and encoded size): quality 95 gives 0.420/255 error, 98 gives **0.238** for ~1.34x the bytes, 99 gives 0.162 for ~1.65x, and 100 gives 0.129 for ~1.96x. 98 is the knee of that curve — it roughly halves the error for a third more disk, whereas continuing to 100 buys less than half that improvement again for nearly double the original size. The default is now 98; `--jpeg-quality` still accepts anything in 1-100, so 95 and 100 are both one flag away. Note the source HEICs are 8-bit **4:2:0** chroma and the JPEG encoder writes 4:2:0 as well, so no colour resolution the original held is discarded — the quantization error above is the whole of the loss. Files that are *already* JPEG/PNG/MOV are moved, never re-encoded, so this changes nothing for them. Two independent default literals had to change together (`Settings.jpeg_quality` and `HeicConverter.__init__`'s own default, which cannot yet share one source without moving `Settings` to a neutral module — issue #67), and a new test now asserts the two agree so a future drift between them is visible rather than silent. The issue #40 measurements quoted in `heic_converter.py`'s comments still say "at quality 95" because that is the quality they were taken at; they describe the `optimize` pass, which changes no pixels at any quality.
- **Progress Bars Now Reflect Real Per-File Work (Issue #14)**: `process_with_progress` used to create a `convert_task` and an `organize_task` with `total=None` and never advance either — for a 300-file HEIC batch (several minutes of libheif decode), the user watched two indeterminate spinners convey no progress at all, then both jumped to 100% at once around the single blocking `process_all_files` call, exactly the kind of stalled-then-snapping bar that invites interrupting a tool that deletes originals mid-run. The fix drives both bars from actual per-file completions. `FileProcessor` gained a new `ProgressReporter.on_heic_converted(path)` hook, fired once per HEIC file as its own conversion attempt finishes and strictly before that file's `on_file` call. Its firing point depends on batch size so it stays truthful either way: for a batch at or above `HEIC_PARALLEL_THRESHOLD`, every HEIC file converts up front in the issue #42 process pool, so the hook fires from inside that pool's `as_completed` loop (and from the `BrokenProcessPool` backfill loop) as each future actually completes — reporting live progress *during* the expensive parallel phase itself, not after the much cheaper sequential place phase catches up to it; below the threshold each HEIC converts inline, so the hook fires there instead, once per file, immediately before its `on_file`. Firing progress from `as_completed` does not touch the #42 equivalence guarantee: the pool's returned `path -> (output, error)` map is keyed by path, not completion order, and the sequential place phase still walks `processable_files` in its own fixed order regardless of which worker happened to finish first, so callback timing is a pure side channel with no effect on landing paths, collision resolution, or failure accounting. `on_categorized`'s `stats` dict now carries an additional `'heic'` key (the processable HEIC count, not itself a categorization category) so a reporter can size a conversion-specific total independent of the move/organize total, and `on_file`'s `action` argument — a fixed `"process"` placeholder since issue #13 introduced the seam — is now `"convert"` for a HEIC file or `"move"` for everything else (quarantined and unknown-routed files included), determined from the file's own extension. `_CLIProgressReporter` uses both: a "Converting HEIC files..." bar sized to the real HEIC count (shown only when there is HEIC work that will actually run — suppressed both when the batch has no HEIC files *and* on a dry run, since a dry run converts nothing at all and a spinning `0/N` there would read as work pending or hung rather than as the deliberately-skipped phase it is) advances via `on_heic_converted`, and an "Organizing files..." bar sized to the real processable-file count advances via `on_file`; both bars show the file currently being handled in their description (`Converting IMG_1002.HEIC...`), and both totals are real numbers from the start — including `0` for an all-sidecar batch, which now renders as a concrete, immediately-settled bar instead of the old `processable_total or None` fallback's indeterminate spinner (`0` is falsy, so that fallback silently discarded a real, correct zero) — so the old `total or 1` placeholder fallback and the duplicated `progress.update(...)` block are gone along with the single generic bar they belonged to. The HEIC count and the pool's conversion input are now computed by one shared `FileProcessor._collect_heic_files` helper rather than two independently-maintained traversals, since the conversion bar's correctness *is* the equality of those two sets — a single source of truth means they cannot drift apart and leave the bar hanging short of its total or overshooting it (`rich` does not clamp `completed` to `total`). Every filename entering a bar description is reduced to its basename and passed through `safe_markup` before display, since `rich`'s `TextColumn` parses the fully-formatted description as markup on render — the same untrusted-filename invariant issue #9 established elsewhere. Measured rather than assumed: an isolated microbenchmark of the changed hook body (`update(description=...)` + `advance()` against a live 10 Hz-refreshing `rich.Progress`, vs. the old `advance()`-only call) shows real per-call overhead — roughly 3–4x costlier in isolation — but at an absolute scale of about 1 microsecond per file; end-to-end (`CLIInterface.process_with_progress` over a real batch of plain JPEGs, median of several runs, pre-#14 checkout vs. this change) the difference at 300 files was old 0.1131s vs. new 0.1148s, and at 1,000 files old 0.7586s vs. new 0.7654s — both under 1.5%, smaller than the run-to-run spread measured on the old code alone, so `rich` refresh overhead stays negligible at these batch sizes. New tests assert `on_heic_converted` fires exactly once per HEIC file on both the pooled and inline paths (and never in a dry run), that every pooled conversion completes before any file is organized, that `on_categorized`'s stats carry the HEIC count, that `on_file`'s action reflects convert vs. move, that the CLI's convert bar reaches its real total end to end through the pool's `as_completed` loop (not just the small inline-path batch a first pass covered), that the convert bar is absent on a dry run and on an all-sidecar batch's organize bar carries a real `0` total, and that both CLI bars render hostile filenames as literal text rather than parsing or swallowing them.
- **Pipeline Orchestration Moved Out Of The Presentation Layer (Issue #13)**: `CLIInterface.process_with_progress` is a presentation object, yet it drove the pipeline — it reached into three *private* `FileProcessor` methods (`_scan_export_directory`, `_delete_sidecar_files`, `_generate_summary`) **and** separately called the public `process_all_files`, which re-scans, re-categorizes, and re-deletes sidecars internally. So scanning, categorization, sidecar deletion, and summary generation each ran **twice** per run (the structure that produced the 1.0.0 duplicate-processing bug), `_generate_summary` was called twice with the first result discarded, and a `progress.update(...)` block was duplicated verbatim. `FileProcessor.process_all_files(dry_run=False, progress=None)` is now the single public entry point for a whole run — scan, categorize, delete sidecars, process, and return the summary — and `CLIInterface` calls only that plus public accessors, reaching into **zero** `_`-prefixed members of `FileProcessor` or its collaborators. Each stage now runs **exactly once** per run. A new, documented `ProgressReporter` seam (in `src/file_processor.py`) lets the presentation layer render and gate a run without owning the loop: `on_no_files()` (scan found nothing), `on_categorized(total, stats) -> bool` (fired once after the single categorization pass with the scanned total and stats; returning `False` aborts the run before any sidecar is deleted or any file is touched — the confirmation seam), and `on_file(path, category, action)` (fired once per processable file as it is handled, never for sidecars). Every hook has a no-op/permissive default, so `progress=None` runs the pipeline headless exactly as before and every existing caller and test is unaffected. `CLIInterface` supplies a `_CLIProgressReporter` that renders the discovery table from the single categorization (no second `batch_categorize`), runs the confirmation prompt, and advances a minimal per-file progress bar — the seam issue #14 will flesh out into real per-phase bars. All observable behavior is preserved: landing paths and collision resolution (#6), verify-before-delete (#7), the parallel HEIC phase (#42), quarantine (#58), unknown routing (#29), dry-run parity (#10), and the exit-code/summary/cancellation semantics (#31). New tests assert scan/categorize/sidecar/summary each run exactly once per confirmed run (they would each be >1 against the old double-invocation), that the reporter fires the total once and once per processable file, and that declining at `on_categorized` aborts before any side effect.
- **HEIC->JPEG Encoding No Longer Pays For `optimize=True` (Issue #40)**: `HeicConverter.convert_heic_to_jpeg` hardcoded `'optimize': True` in the JPEG save kwargs, which tells libjpeg to run a second entropy-coding pass to build optimal Huffman tables. It does not change a single pixel — output is numerically identical, only the coding differs — yet a performance audit measured HEIC conversion at 97.8% of total wall time and this one pass at +71.5 ms per real HEIC (+152% on the encode step, +39% of the whole conversion cost) for only a ~2.3% smaller file. Dropping it makes a HEIC-heavy run **~1.31x faster end to end** (a 100-file / 55-HEIC batch fell from ~16.3s to ~12.6s in the audit) in exchange for slightly larger JPEGs — the right trade for an archive tool on a Mac with terabytes of disk. `optimize` is now off by default and promoted to a `HeicConverter(optimize=False)` constructor argument alongside `jpeg_quality`, so byte-for-byte parity with the old output remains one flag away for anyone who wants it. The conversion still produces a valid, dimension- and EXIF-preserving JPEG (`verify_conversion` unchanged and still green). Size trade-off, measured here on a synthetic detail-rich 2000x2000 HEIC (gradient + per-pixel noise, a proxy that overstates the delta versus the audit's real-photo 2.3% because random noise gives the Huffman optimizer more to squeeze): output grew **+5.15%** (2,242,405 -> 2,357,939 bytes) with optimize off. A new test pins the default to `optimize=False` at the `Image.save` boundary while still asserting the produced JPEG verifies, so a default that quietly turned optimization back on would fail.
- **Dependencies Carry Upper Bounds (Issue #15)**: Every dependency was previously a floor with no ceiling (`pillow>=10.0.0`), so a future major release — Pillow in particular has changed its EXIF APIs across majors — would be accepted silently. Each dependency now pins a conservative upper bound at the next major above the range known to work (`click>=8.0.0,<9`, `pillow>=10.0.0,<12`, `pillow-heif>=0.10.0,<1`, `python-dateutil>=2.8.0,<3`, `rich>=13.0.0,<15`, `hachoir>=3.1.0,<4`). `pyproject.toml` is the single source of truth for the dependency list; `requirements.txt` is retained as a thin, mirrored pointer for the older `pip install -r requirements.txt` workflow.
- **`main.py` Import Simplified (Issue #15)**: Removed the `sys.path.insert` manipulation and the dual `try/except ImportError` fallback from `main.py`, which existed to support a `python src/main.py` invocation that never actually worked (the rest of `src/` uses `from src.…` imports with no installed package). A single clean `from src.cli_interface import …` remains; `python -m src.main` and the installed `tm-monthly-backup` console command are the supported invocations.
- **Video Metadata's Fast Path Actually Fires Now (Issue #16)**: `ExifHandler._extract_video_timestamp_hachoir`'s primary lookup probed for a `creation_date` attribute via `hasattr`/`getattr` on hachoir's `Metadata` object, but hachoir exposes its fields only through a `get(key)` method — the object never has any of the four attributes tried (`creation_date`, `date`, `creation_time`, `media_creation`; only the first is even a real hachoir field), so the probe was silently dead for every video ever processed and the function unconditionally fell through to materializing the whole metadata set as text via `exportPlaintext()` and regex-scanning it line by line — real work paid, unnecessarily, by every video whose Apple `com.apple.quicktime.creationdate` key (issue #28's preferred source) is absent, i.e. every non-iPhone-recorded clip such as a screen recording or an AI-generated video. The lookup now calls hachoir's real `metadata.get('creation_date')` API, guarded against the `ValueError` hachoir raises (rather than returning `None`) when the key carries no value; `exportPlaintext()` remains only as a genuine last resort, now reached only when the direct lookup finds nothing usable. - **Photo And Video Metadata Precision (Issues #70, #71, #72)**: the whole-branch review's non-destructive findings -- each one a permanent *mislabel* of a real photograph rather than a loss, which is why they were filed separately and fixed after the data-safety work.
  - **`ScreenRecording_` filenames are read month-first (#70).** Two real conventions collide inside one filename pattern, and the digits alone cannot separate them when both leading fields are ≤ 12: `Facetune_09-02-2024-...` is genuinely day-first, but `ScreenRecording_03-05-2024 09-15-00_1.mp4` is month-first. Issue #51 introduced the pattern for Facetune and tried day-first first for everything, so a July 1 screen recording was filed as **January 7** whenever its container metadata was missing -- which is common, since a re-muxed file often carries a 1904 `mvhd` that #62 correctly rejects, dropping straight to the filename. The screen-recording convention is established rather than guessed: that file's own `mvhd` reads 2024-03-05 13:15:00 UTC = 08:58:01 EDT, exactly the time in its name. The reading order now comes from a marker in the filename; an unrecognized generator keeps #51's day-first default, because there is no evidence either way for a generator this project has never observed.
  - **A video filename's local time now beats the UTC `mvhd` (#72)** — when it can be *confirmed* to describe the same instant, meaning the two differ by a plausible UTC offset (a whole number of quarter-hours within ±14h, which admits every real zone including the `:30` and `:45` ones). Before this, two screen recordings in a real archive were filed four hours late, and any capture after 20:00 EDT landed on the **wrong calendar day**. The confirmation is what makes preferring the filename safe: a DJI epoch-suffix name against a real `mvhd` is correctly ignored rather than allowed to outrank container metadata. Depends on #70 — without it, trusting the filename here would have turned "four hours late" into "six months wrong". Also closes the sibling gap: the 1904 QuickTime zero-epoch sentinel was checked only on the `mvhd` path, on the reasoning that Apple's `creationdate` key "has no zero-epoch encoding of its own" — true of the encoding, but not of the value, since a re-muxer synthesizing that key from a zeroed `mvhd` writes the literal `1904-01-01T00:00:00+0000`, which parses cleanly and would have been filed as `videos/1904.01.01.00.00.00.mov`.
  - **Real photographs are no longer filed as AI-generated (#71).** Three independent routes sent a genuine photo to `backup/generated/`, a directory you have no reason to look in. (1) `FileCategorizer` and `ExifHandler` disagreed about IFD0 `DateTime`: the timestamp module accepts it as a capture time and will *name the archived file from it*, while the categorizer treated its presence as no evidence of capture at all — so a scanned 1950 print re-saved by Photoshop (which writes `Software` + IFD0 `DateTime` and no `DateTimeOriginal`) landed as `backup/generated/1950.06.01.12.00.00.jpg`, named from the very timestamp ruled non-existent. (2) The editing-software list was matched as a bare substring, exactly the bleed issue #8 fixed for AI markers with `\b`: `canva` is a substring of `Canvas`, so `Software = "Canvas X 2019"` flagged a drawing as generated. (3) The UUID-stem rule fired unconditionally, so unlike the editing-software rule (which has always required "and no capture timestamp") real EXIF could not rescue the file — an Apple asset-UUID export carrying a good `DateTimeOriginal` was filed as generated. That rule also over-matched: `uuid.UUID` strips all hyphens and accepts any 32 hex digits, so an MD5-named photo and a bare run of 32 digits both qualified, despite the docstring claiming segment lengths were validated. Every fix is paired with a true-positive test — loosening a detector until it stops firing is not a fix.

- **The hachoir stream is closed when parser creation fails (Issue #66)**: hachoir's `createParser` opens the file, then closes its stream only when `guessParser` *returns* `None` — nothing closes anything when either step *raises*, and a zero-byte `.mov` raises from inside `FileInputStream` itself, *after* the open. Two things turned out to be different from the issue's description, both established by measurement rather than assumed. The leak is not around `guessParser`, so wrapping that call fixes nothing; the handle is now opened by this project and passed in, so the function owns the descriptor on every path. And the scope is narrower than reported: on CPython refcounting reclaims the abandoned handle as soon as the exception is discarded, so the current call path — which logs and drops it — does not leak today. Findings go to a new `_landing_discrepancies` accumulator — deliberately **not** `_failed_files`, since those files are already counted in `files_processed` and adding them to the failure bucket would break the very identity the audit exists to check — surfaced as `landing_discrepancies` / `landing_discrepancy_list` and reset by `clear_processing_state` like every other per-run accumulator (issue #35). `is_unqualified_success` (the single success predicate, issue #31) gained the condition, so a discrepancy withholds `Success!` from both the results banner and `main.py`'s standalone line; the banner is ranked **above** "With Errors" and styled bold red rather than yellow, because every other condition reports an outcome the tool knows about accurately whereas this one means the table underneath it is unreliable, and a new detail table names each path, labels whether it was missing or duplicated, and tells the user in plain terms to verify `backup/` by hand before deleting anything from `export/` or from Photos. Two deliberate non-behaviours: a **zero-byte landing is not flagged**, even though it is the signature of an orphaned reservation, because a legitimately empty source file produces the same thing and a check that cries wolf on every run over a personal archive teaches the user to ignore the banner (the same reasoning that kept a bare `.DS_Store` from demoting it in issue #30); and **dry runs are skipped outright via the explicit flag** rather than by inferring "nothing to audit" from an empty `_processed_files` — a dry run never appends there, but `_quarantine_file` *does* record an entry whose `final_path` was only resolved and never created, so the emptiness inference would have reported a phantom discrepancy for every undecodable file in a dry run and broken the issue #10 parity this audit has no business touching. Also added: `scripts/snapshot-export.py`, a read-only pre-run snapshot of `export/` (path, size, first-1 MiB SHA-256) and a post-run reconciler that matches every non-HEIC source byte-for-byte against the archive — the missing "before" picture that made the original question unanswerable. 14 new tests drive the real `process_all_files` entry point and the real move seam, covering a clean run reporting zero, a landing deleted between the move and the audit, a forged duplicate, a duplicated-and-absent path reporting each problem exactly once, quarantined landings, both dry-run cases, the reuse contract across two runs on one instance, and no-aliasing of the reported list; 4 more cover the display layer. All 18 are mutation-verified: stubbing `_verify_landings` to `return` fails 7, and removing the `if dry_run` guard fails the dry-run quarantine test.
- **`--keep-heic` Removed Entirely (Issue #65)**: Issue #41 added `--keep-heic`, which left a converted HEIC's original in `export/` instead of deleting it once its conversion was verified good. Issue #65 found that a retained original is invisible to this tool as "already archived": nothing distinguishes it from a brand-new file, so the *next* run rescans it, re-converts it, reads the same EXIF capture timestamp, finds the previous run's `backup/photos/<that timestamp>.jpg` already occupied, and the `O_CREAT | O_EXCL` collision-resolution loop (issue #6) bumps the new landing name forward by a second — filing a **second, duplicate copy of the photo in the archive, under a timestamp that is not its capture time**, repeating on every subsequent run for as long as the original stayed in `export/`. Rather than adding a skip-if-already-archived check to fix retention in place, the project owner decided the flag itself should go: convert-then-delete is this tool's intended design, the retention flag was an escape hatch never actually needed, and removing it eliminates both the bug and the ongoing maintenance surface. `--keep-heic` never shipped in a release — it existed only on this unreleased branch — so no user loses a feature; the CHANGELOG's issue #41 entry above is amended to document only `--jpeg-quality`. The `Settings.keep_heic` field, the `--keep-heic` CLI option, the unconditional-versus-conditional delete gate in `FileProcessor._process_single_file`, and the `CLIInterface.display_results` "HEIC Originals Retained" row are all removed; the delete of a HEIC's original is unconditional again once its conversion has passed issue #7's verify-before-delete gate, exactly as it was before issue #41, and that gate itself — verify, then delete only on success, with a failed verification recorded as a failure and the original left in place — is untouched and still covered by a dedicated test.
- **Declared Python Floor Raised To 3.9 To Match What The Code Actually Requires**: `pyproject.toml` declared `requires-python = ">=3.8"` (as the issue #15 entry above records) while `FileProcessor._convert_heic_files_parallel`'s `KeyboardInterrupt` handler calls `executor.shutdown(wait=False, cancel_futures=True)` — and `cancel_futures` was added to `Executor.shutdown` in **Python 3.9**. On 3.8 that call raises `TypeError` *from inside the interrupt handler*, so pressing Ctrl-C during a HEIC batch large enough to spawn the process pool (issue #42's 8-file threshold) replaced the clean cancel-and-teardown with a `TypeError` traceback, potentially orphaning workers — the failure landing precisely where the code was trying to shut down safely. The declaration was therefore not merely optimistic but wrong: any 3.8 install would have accepted the package and then failed on interrupt. The floor is now `>=3.9`, which is the minimum the code has genuinely required since issue #42 landed, and this declaration supersedes the one described in the issue #15 entry above. Python 3.8 reached end-of-life in October 2024, so this drops no supported interpreter. Nothing else changed: the call site, the interrupt semantics, and the pool bounds are untouched, and the codebase remains free of any 3.10+ syntax (no `match`, no runtime `X | Y` unions), so 3.9 is a real floor rather than a nominal one.
- **Filename Timestamp Fallback Now Recognizes Space-Separated And Day-First Export Names (Issue #51)**: `ExifHandler._extract_timestamp_from_filename` is the second hop in the fallback chain (EXIF -> filename patterns -> `st_birthtime` -> `st_mtime` -> `datetime.now()`), and a miss here means a re-downloaded or copied file gets named from the *copy* date rather than the capture date — a permanent mislabel, since the tool renames the file and deletes the original. Auditing the repo's own `export/` found the two supported patterns missed 314 of 326 filename-pattern candidates, including two shapes that plainly carry a date: the standard macOS export/screenshot form `2011-03-09 18-20-30.jpg.jpeg`, where a space (not `_`/`-`) joins the date and the time and the old pattern's separator character class didn't include whitespace; and Facetune's `Facetune_09-02-2024-11-22-33.heic`, which is `DD-MM-YYYY-HH-MM-SS` — day-first — while the existing pattern only understood a leading four-digit year. The date/time separator in the year-first pattern now also accepts whitespace (`[_\-\s]`), and a new day-first pattern handles `DD-MM-YYYY-HH-MM-SS` names. Day-first is genuinely ambiguous with month-first whenever both leading fields are <= 12 (`04-07` could be day=4/month=7 or month=4/day=7), so both readings are attempted — day-first first, matching the Facetune convention — and only a reading that produces a real calendar date (rejecting, e.g., a month of 20 or a day of 31 in November) is accepted; whichever reading resolves is logged at INFO so a wrong guess on a truly ambiguous name is auditable rather than silent. The fail-closed contract of the whole fallback chain is unchanged: a filename where *neither* reading produces a valid date, or where a pattern matches but yields an out-of-range date (e.g. month 13), still returns `None` and falls through to the filesystem timestamp rather than guessing a valid-but-wrong date — verified there is no filename shape that parses to a wrong-but-valid date under either pattern. The DJI-style `..._105_1700000000000_photo...` filename, whose 13-digit epoch suffix must continue to be ignored rather than mistaken for date digits, still resolves via the unchanged compact `YYYYMMDD_HHMMSS` pattern. EXIF extraction and the video metadata path (including the issue #28 local-wall-clock-over-UTC rule) are untouched.
- **PNG AI/C2PA Detection No Longer Forces A Full Pixel Decode (Issue #44)**: `FileCategorizer._png_text_has_ai_provenance` probed a PNG's text chunks via `img.text`, and Pillow's `PngImageFile.text` property calls `self.load()` before it will return anything, because tEXt/iTXt chunks are legally permitted to appear *after* IDAT and Pillow refuses to report a partial answer — so merely checking whether a PNG carries AI/C2PA markers silently decoded the entire image into a bitmap, at the same cost as an explicit `load()`, purely to read metadata that in practice every mainstream tool writes before IDAT. A performance audit measured the `.text` probe at 29.29 ms per real PNG (1.2–8.4 MB, best-of-3), statistically identical to a full `load()` at 29.15 ms, versus `im.info` — a plain dict Pillow already populates while parsing the chunk stream during `Image.open()` — at 0.05 ms for the same chunks, roughly 585x cheaper; on the audit's own export this cost 249 ms of a ~53s run (0.5%), and would have scaled to ~1.9s once issue #22 widens AI detection to every PNG rather than just non-screenshots. `_png_text_has_ai_provenance` now reads `img.info` instead of `img.text`, measured on a synthetic 2000x2000 noise PNG carrying a real `tEXt` marker and `eXIf` chunk to show the `_is_generated_content` body dropping from 28.47 ms to 0.03 ms (confirmed against the pre-fix code the same way). Because `img.info` — unlike `img.text` — also carries every *non*-text PNG ancillary chunk Pillow parses before IDAT (`icc_profile` and raw `exif` land there as `bytes`, never as `str`, along with `transparency`/`dpi`/`gamma`/`aspect`), the scan only considers entries whose value is a `str` (`PIL.PngImagePlugin.iTXt` is itself a `str` subclass, so unicode iTXt values are still included) before running the marker search, so a binary chunk can never widen the match surface the way naively stringifying every `info` value would — this keeps the change a how-we-read change, not a what-we-match change. The trade-off is a text chunk written strictly *after* IDAT would now be invisible to this check; no mainstream generator does that — C2PA manifests and generator `Software`/`parameters` chunks are written in the header — so detection is unaffected in practice, and the #8 precision rules this function enforces (provenance matched against identifiable text-chunk **keys** `c2pa`/`parameters`, values matched only at **word boundaries** against the curated marker set, UUID stems validated by `uuid.UUID(...)`) are preserved exactly and unmodified; every existing categorization test still passes untouched, and five new tests assert directly against Pillow's real decode boundary (`Image.tile`, which `load()` empties and nothing else does) that probing a PNG's provenance — whether it matches, matches on a bare key, matches nothing, or coexists with binary ICC-profile/EXIF chunks (including one deliberately carrying a marker word in its byte representation) — never empties it and never mistakes a binary chunk's bytes for text provenance.
- **Dry Run Now Predicts Exactly What A Real Run Does**: `--dry-run` is the only safety mechanism a user has before this tool irreversibly renames, moves, and deletes their photo library, so it must report the *exact* plan a real run would execute — yet the HEIC branch of `FileProcessor._process_single_file` reported the wrong destination for the file type the tool converts most often. In dry-run mode the converted-JPEG path was computed into a local (`Path(file_path).with_suffix('.jpg')`) that was **discarded** — `current_path` was reassigned only on the real-run branch — so `file_extension = Path(current_path).suffix` still yielded `.heic`, and the run reported `backup/photos/<timestamp>.heic`: a filename that will never exist, on a file that always lands as `.jpg`. Both modes now derive a single `planned_extension` (`.jpg` for any HEIC, since the converter's output and the timestamp-derived final name make the intermediate name irrelevant), so the dry-run plan carries the same extension a real run produces. The dry run reads the timestamp from the original `.heic`, whose EXIF is identical to the converted JPEG's, so no conversion — and no disk write — is needed to predict the exact landing path. The previously fixed collision seeding (issue #6, dry-run reservations seeded from disk and tracked in memory), quarantine reporting (issue #58), and unknown-file routing (issue #29) already gave the other categories dry/real parity; this closes the last divergence. A new parity test asserts the set of planned `(category, target)` a dry run reports equals what a real run actually lands for a mixed input set — photo, HEIC, screenshot, video, unknown, undecodable, and two colliding timestamps — and that a dry run performs zero `shutil.move`/`shutil.copy2`/`os.remove`/`os.makedirs` calls and materializes no backup tree.
- **Crafted Filenames Can No Longer Abort The Run Or Corrupt Output Through `rich`**: Filenames arrive untrusted — from iCloud, AirDrop, downloads, and manual renames — and flowed straight into `rich` markup contexts via f-strings, where square-bracket text is parsed as styling markup. A name carrying an unmatched closing tag (`photo[/].jpg`) raised `MarkupError`; because `FileCategorizer.categorize_file`'s "Unknown file type" warning runs inside `batch_categorize`, which is **not** wrapped in a `try/except`, that exception propagated to the top-level handler in `main.py` and **aborted the entire run**. A name carrying a *valid* tag (`IMG_[bold red]1234.jpg`) was silently swallowed instead, so the bracketed text vanished from logs and the summary — and the same crash could fire from inside `display_failures` while the tool was already reporting an error. Beyond markup, raw ANSI/control sequences in a filename reached the terminal unfiltered and could reposition the cursor or rewrite already-printed output. Untrusted values are now neutralized at every boundary: a new `sanitize_for_display` strips ANSI escape and C0/C1 control sequences (leaving ordinary text, brackets included, intact), and `safe_markup` layers `rich.markup.escape` on top for the markup-parsed contexts. `Console.print` f-strings (`check_directories`) and `Table.add_row` cells (`display_failures`) now pass through `safe_markup`; the literal `Text.append` rows in `display_missing_exif_warning`, which never parse markup, are stripped of control sequences without escaping (which would corrupt them). The logging path is closed at a single boundary: `RichHandler` is configured with `markup=False` — the tool never emits intentional markup through the logger, so disabling it costs nothing — and a `_SanitizingLogFilter` collapses each record to its final text and removes control sequences, so no log message can drive the terminal regardless of how a call site formats. Log call sites carrying untrusted filenames across `file_processor.py`, `file_categorizer.py`, `heic_converter.py`, and `exif_handler.py` were additionally converted from f-strings to lazy `%s` formatting, keeping the untrusted value a parameter rather than part of the format string. A `photo[/].jpg`-style path now processes end to end without raising and appears literally in the summary; a `[bold red]` name is preserved verbatim; ANSI sequences are stripped from all output.
- **Symlinks Archive The Photo They Point At, Not The Link Itself**: A symlink in `export/` pointing at a real image is intentionally kept by the scan (issue #54's `os.path.isfile` follows the link and sees a regular file), but `FileProcessor._process_single_file` then filed it with `shutil.move`, which falls through to `os.rename` on a same-filesystem move — relocating the **symlink itself**. `backup/photos/<timestamp>.jpg` became a symlink pointing back at the original target rather than a copy of the photo, so the archive held a hollow pointer: the run reported success and the file appeared in every listing, but `open()` failed the moment the user tidied the target away (emptied a scratch folder, unplugged the drive it lived on). The failure was even filesystem-dependent — a *cross*-filesystem `shutil.move` copies real bytes instead, so the same input produced a photo or a dead link depending only on where `backup/` sat. Placement now goes through `_place_source_content`, which detects a symlink (`os.path.islink`) and **copies the resolved target's real bytes** onto the reserved destination (`shutil.copy2` of `os.path.realpath(path)`, mirroring the target's mtime), then removes **only the link** from `export/` (`os.remove` on a symlink unlinks the link, never its target). The archived entry is always a regular file carrying the photo's bytes, identical whether `backup/` is on the same volume or another, and it survives the target being deleted afterward. Crucially the target — which a symlink can place entirely **outside** `export/` — is never moved, deleted, or modified; only the link is removed. The same copy-then-unlink applies on every path a symlinked source can take: HEIC targets still convert to a real JPEG (the original-delete step unlinks the link, sparing the target HEIC), undecodable targets quarantine a real **copy** into `backup/corrupt/` under the link's name, and unrecognized targets file a real copy into `backup/unknown/`. A plain regular file is still moved, so `export/` is fully drained as before. The destination-collision safety (issue #6), verify-before-delete for HEIC (issue #7), and lazy-directory guarantees are all preserved.
- **Non-Regular Files No Longer Hang The Run**: `FileProcessor._scan_export_directory` appended every non-hidden entry `os.walk` yielded without checking it was a *regular* file. `os.walk` excludes directories, but its `filenames` list still surfaces FIFOs (named pipes), sockets, and device nodes — non-regular files an untrusted `tar`/`cpio` archive materializes when extracted into `export/`, which is precisely this tool's threat model (a hostile *file*, not a hostile user). Opening a FIFO for reading **blocks until a writer appears**, and there is no writer, so a later `Image.open(...).load()` (the undecodable-file gate, or an EXIF read) stalled the entire run **forever** — `--dry-run` included, since categorization runs before the dry-run branch — with only a never-advancing spinner and the photo beside it never backed up. The scan now rejects any entry that is not a regular file with `os.path.isfile(path)`, a `stat`-based check that **never opens the file** (so the check itself cannot block) and returns `True` only for regular files and symlinks whose target is a regular file. FIFOs, sockets, device nodes, and broken symlinks are skipped and logged; a symlink pointing at a real image is still kept for normal processing. The existing hidden-file skip and hidden-directory pruning are unchanged.
- **Hidden Directories Are No Longer Walked, Archived, Or Deleted From**: `FileProcessor._scan_export_directory` skipped hidden *files* (`filename.startswith('.')`) but never pruned hidden *directories*, so `os.walk` descended straight into every dot-directory under the export root — the macOS system trees (`.Trashes`, `.Spotlight-V100`, `.fseventsd`, `.DocumentRevisions-V100`) and a repo drop-off's `.git`. Any non-hidden file inside one became a full pipeline participant: `.Trashes/deleted.jpg` (a photo the user deliberately threw away) was resurrected into `backup/photos/` under a fabricated timestamp, `.git/objects/pack/x.jpg` was archived as a photograph, and — worst — an `.aae` sidecar found inside a hidden tree was **permanently deleted** by `_delete_sidecar_files`, which runs first and does not care where a file came from. On a macOS export volume these directories are ubiquitous, files are *moved* (mutating the source trees), and the `.aae` deletion is irreversible. The scan now prunes hidden directories in place during the walk (`dirs[:] = [d for d in dirs if not d.startswith('.')]`), the documented `os.walk` mechanism for skipping subtrees, so a hidden directory at *any* depth is never descended into, its contents are never categorized, archived, or discovered for sidecar deletion, and it is left exactly as found in `export/`. The existing leaf-level hidden-file skip is retained, and normal (non-hidden) subdirectories are still walked and their photos processed.
- **Undecodable Files Are Quarantined, Not Archived As Photos**: `FileProcessor._process_single_file` never established that a file carrying a photo extension was decodable media. It asked `ExifHandler.extract_timestamp` (which returns `None` on any failure), fell back to filesystem mtime, then renamed and moved — so a zero-byte `empty.jpg`, a text file named `.png`, or a JPEG truncated by an interrupted iCloud/AirDrop download was renamed to a fabricated timestamp and filed into `backup/photos/` as if it were a photograph. The rename is the damage: `empty.jpg` at least announced itself, but `2026.08.01.12.00.44.jpg` is indistinguishable from a real photo in a directory of thousands, and the archive is the only copy. Image-typed files (`PHOTO`/`SCREENSHOT`/`GENERATED`) whose extension Pillow can decode (`.jpg`/`.jpeg`/`.png`/`.gif`/`.tiff`/`.tif`/`.bmp`/`.webp`) are now decode-verified before the rename: `Image.open(path).load()` forces a full pixel decode, which — unlike the lazier `Image.verify()` — actually catches a JPEG truncated to half its bytes (`verify()` validates structure but never reads the pixel data, so it passes a truncated JPEG); a zero-byte file is rejected up front. Files that fail are moved to `backup/corrupt/` under their **original filename** (a corrupt file has no reliable capture time, so its name is the only clue for recovery), never overwriting a name already there (`name (1).ext` disambiguation, reusing the atomic `O_CREAT | O_EXCL` reservation from issue #29), with the directory created lazily so it is never an empty phantom. RAW formats (`.dng`/`.cr2`/`.nef`/…) are deliberately excluded from the gate — Pillow cannot decode them, so a valid RAW would be falsely quarantined — and HEIC/HEIF are left to their existing conversion-verification path (issue #7). Quarantined files are reported as a distinct outcome — counted in a new `files_quarantined` tally, neither a clean "processed" nor a tool "failure" — and the results banner no longer reads an unqualified "Success!" when files were quarantined; `--dry-run` reports the same quarantine decisions a real run would make without moving anything. Exactly one full decode is performed per file (the downstream EXIF read only touches the header), so no file is decoded twice.
- **AI-Content Detection No Longer Misfiles Ordinary Photos**: `FileCategorizer._is_generated_content` scanned every PNG text chunk for the bare substrings `['gpt', 'chatgpt', 'openai', 'c2pa', 'ai', 'generated']`. Because `'ai'` was matched with `in` against the whole lowercased value, it hit inside ordinary English words — ch**ai**r, tr**ai**l, po**rtrai**t, det**ai**l, r**ai**n, Sp**ai**n — so a real photo captioned "Portrait of a chair on a trail" was categorized `GENERATED` and routed into `backup/generated/`, where a manual cleanup could delete it unnoticed; `'generated'` matched captions just as broadly. Detection is now precise: provenance is matched against identifiable PNG text-chunk **keys** (`c2pa`, `parameters` — the Stable Diffusion / AUTOMATIC1111 key), and values are matched only at **word boundaries** against a curated marker set (`chatgpt`, `openai`, `gpt-4`/`gpt-4o`, `dall-e`/`dall·e`, `midjourney`, `stable diffusion`, `firefly`, `c2pa`). The bare `'ai'` and `'generated'` tokens are dropped entirely. UUID-style filenames are now validated by parsing the stem with `uuid.UUID(...)` inside `try/except ValueError` instead of the shape-only `len == 36 and four hyphens` check, which accepted any 36-character name with four hyphens regardless of its hex digits. The editing-software heuristic (editing `Software` present with no original capture timestamp) now reads `DateTimeOriginal`/`DateTimeDigitized` from the Exif **sub-IFD** as well as IFD0 (issue #25): reading only IFD0 never found the sub-IFD capture time, silently collapsing the intended "edited AND no capture time" rule into "any edited image" and misfiling genuinely edited photos that had kept their timestamp. Genuine AI/C2PA content is still caught; ordinary photos carrying those words in a caption are not.
- **Videos Named From Their True Local Capture Time, Not UTC**: `ExifHandler._extract_video_timestamp` named MOV/MP4 files from hachoir's `mvhd` creation_time, which QuickTime defines as **UTC**. Apple, however, records the real local wall-clock capture time — with its UTC offset — in the `com.apple.quicktime.creationdate` metadata key, and the tool never read it. Every video shot after roughly 8pm Eastern therefore rolled forward a calendar day: a clip shot 2026-07-04 21:33 EDT was stored as `2024.06.16.01.33.03.MOV`, filed under July 5th when it was shot on the 4th, with the original filename destroyed and no manifest to recover it. The extractor now prefers `com.apple.quicktime.creationdate`, parsing the offset-bearing ISO-8601 string and keeping the **local wall-clock reading** (`21:33:03` stays `21:33:03`) so a video and a photo captured at the same instant share the same `YYYY.MM.DD.HH.MM.SS` stem. hachoir does not surface this key, so the value is read directly from the QuickTime/MP4 box structure (`moov` → `meta` → `keys`/`ilst`), handling both the QuickTime and ISO `meta` layouts and skipping large boxes without loading them. The hachoir/`mvhd` UTC path remains only as a fallback for containers that lack the Apple key; that fallback can still be off by the UTC offset — a pre-existing limitation this change does not worsen. Image/EXIF timestamp handling is untouched.
- **Unrecognized Files Are Now Actually Filed (No Silent Leave, No Phantom Directory)**: `FileCategory.UNKNOWN` was categorized, counted, rendered against `backup/unknown/` in the results table, and its directory was even pre-created — but `get_processable_files` omitted it from the processable set, so `process_all_files` never moved an unknown file. Unrecognized files were silently left in `export/` while `backup/unknown/` sat empty forever, yet the summary counted them and the exit code implied a clean, fully drained run — exactly the mismatch that made the documented cleanup step destructive. Unknown files are now genuinely routed into `backup/unknown/`. Because they carry no metadata to derive a timestamp from, they keep their **original filename** rather than being renamed to a fabricated timestamp that would erase the one identifying detail available for manual review. A name already present there is preserved by disambiguating the incoming file as `name (1).ext`, `name (2).ext`, … using the same atomic `os.open(..., O_CREAT | O_EXCL)` reservation the timestamped path uses, so an unknown file never overwrites one a prior run filed. The directory is created lazily, only when a file actually lands in it, so `backup/unknown/` is never an empty phantom. `get_processable_files` now derives its categories from the `FileCategory` enum (everything except sidecar) instead of a hand-maintained list, so a newly added category can never again be silently dropped. `ensure_target_directories` no longer eagerly creates `backup/unknown/`. Docs (`README.md`, `docs/cli-usage.md`, `docs/troubleshooting.md`) already described this destination and now match the code.
- **Every Failure Is Now Accounted For (No Silent Success)**: When `HeicConverter.convert_heic_to_jpeg` returned `None` (a failed conversion), `FileProcessor._process_single_file` `return`ed without recording anything, so the unconvertible `.heic` was silently dropped: it was left in `export/`, `files_failed` stayed `0`, the summary printed "Processing Complete - Success!", and the process exited `0` for a run that had not processed the file. The returns-`None` branch now records `('convert_heic', path, 'HEIC conversion failed')` in `failed_files`, so the file counts toward `files_failed`, appears in the failure table, retitles the summary to "With Errors", and drives a non-zero exit. Every discovered processable file now lands in exactly one bucket — processed or failed — a `files_processed + files_failed == files_seen` invariant asserted in the test suite.
- **Exit Codes Have Distinct, Documented Meanings**: `main.py` exited `1` for both partial per-file failures *and* fatal precondition errors (missing/unwritable/overlapping directories, unexpected exceptions), and a cancelled run was indistinguishable from a clean success because `process_with_progress` signalled "cancelled" and "no files" with an empty dict inferred from falsiness. The exit path now uses an explicit, testable taxonomy (`determine_exit_code`): `0` = every discovered file processed with zero failures; `1` = processing ran but one or more files failed; `2` = precondition failure (missing/unwritable directory, the export/backup overlap rejection, or an unexpected error — nothing was processed); `130` = cancelled by the user (declined prompt or `SIGINT`, per the POSIX `128 + signal` convention). `process_with_progress` now returns a status-tagged result instead of an empty dict, so a declined confirmation can never be reported as success. The exit-code table in `docs/cli-usage.md`, which previously listed `1` twice with conflicting meanings, is updated to match.
- **Backup Files No Longer Overwritten Across Runs**: `FileProcessor` judged filename collisions with `used_timestamps`, an in-memory `set` populated only during the current process and never seeded from what already sat in `backup/`. Because `shutil.move` overwrites its destination silently, two photos processed in *different runs* (e.g. two monthly dumps) that resolved to the same `YYYY.MM.DD.HH.MM.SS` name caused the second run to overwrite — and irrecoverably destroy — the first run's file, while reporting a clean summary and exiting `0`. An attacker who could influence a filename in `export/` could even *aim* the overwrite at a known archive name. Collision detection is now filesystem-authoritative and scoped per target directory: before a file is filed, its destination path is reserved atomically with `os.open(..., O_CREAT | O_EXCL)`, which closes the check-then-move TOCTOU window and can never select an already-present file as the move target. The timestamp is bumped a second at a time until a free path is claimed, and the real file is then moved onto the empty placeholder the reservation created (a failed move drops the placeholder). Each per-directory name set is seeded once from the directory's on-disk contents so resolution does not rediscover conflicts one filesystem probe at a time. A dry run stays side-effect free but now reports the *bumped* path a file would take when its natural name is already occupied, instead of a name a real run would overwrite.
- **Cross-Category Timestamp Collisions Eliminated**: `used_timestamps` was a single flat set shared across every category, so a photo and a video (or screenshot) resolving to the same second were treated as a collision and one was bumped by a second — even though they are written to *separate* directories and can never collide on disk. The resulting filename no longer matched the media's true capture time. Collision tracking is now keyed by target directory (`Dict[str, Set[str]]`), so files in different category directories share no collision namespace and each keeps its exact timestamp; two files in the *same* directory still bump correctly.
- **HEIC Original Verified Before Deletion**: `FileProcessor._process_single_file` deleted the original `.heic` with `os.remove` the instant `convert_heic_to_jpeg` returned a non-`None` path, with no check that the JPEG was actually valid on disk. Because the converter returns its output path immediately after `image.save` without inspecting the result, a truncated write, a zero-byte file, a full disk, or a partial decode all produced a "successful" return — after which the only copy of the original photo was destroyed. The pipeline now calls `HeicConverter.verify_conversion` against the *actual* converted path (the unique `mkstemp` name, not a stale `{stem}.jpg`) before the original becomes eligible for deletion: the JPEG must exist, decode, match the source dimensions, and preserve EXIF. On verification failure the original `.heic` is left in place in `export/`, the unverifiable artifact is removed, and the failure is recorded in `failed_files` so it drives a non-zero `files_failed`. The delete is further deferred until *after* the verified JPEG has landed in `backup/photos/<timestamp>.jpg`, so a failure during the move can never leave the user with neither the original nor a filed copy. Deletion now routes through the single `HeicConverter.cleanup_original_heic` implementation, retiring the inline `os.remove` duplicate; `cleanup_original_heic` was also repaired to verify against an explicit converted path rather than the stale `{stem}.jpg` name.
- **HEIC Conversion No Longer Overwrites Existing Files**: `HeicConverter.convert_heic_to_jpeg` wrote the converted JPEG to a fixed `{stem}.jpg` beside the HEIC. When a real sibling with that name already sat in the export tree — an exact `IMG_1234.jpg`, or an uppercase `IMG_1234.JPG` on a case-insensitive APFS volume — the conversion silently overwrote and destroyed that photo, reporting `files_failed: 0` with no error. Because `os.walk` returns APFS entries in hash order, the loss occurred on roughly half of all same-stem pairs. The converter now reserves a guaranteed-unique output path with `tempfile.mkstemp` (atomic `O_CREAT | O_EXCL`) on the same filesystem, so it can never collide with an existing sibling in either the exact-name or case-insensitive case, and the downstream `shutil.move` to `backup/photos/<timestamp>.jpg` stays a cheap same-volume rename. Callers already use the returned path, so the transient intermediate name is invisible to the final timestamp-derived backup filename.
- **Overlapping Export/Backup Directories Rejected**: The tool now refuses to run when `--export-dir` and `--backup-dir` overlap — the same directory, or one nested inside the other. Because the export tree is consumed in place (sidecars and converted-from HEIC originals are deleted), an overlapping destination let a run re-ingest and destroy its own archive. Paths are resolved with `Path.resolve()` (normalizing symlinked and relative aliases) and compared for equality and containment in both directions. The guard runs on both entry surfaces: `CLIInterface.check_directories` reports the conflict and exits non-zero, and `FileProcessor.process_all_files` raises `ValueError` before scanning so a programmatic caller cannot bypass it.
- **Timestamp Rollover Crash**: `ExifHandler.handle_duplicate_timestamp` no longer raises `ValueError` when incrementing past a second, minute, hour, or month boundary. Replaced the manual `datetime.replace` arithmetic with `timedelta`, which handles all rollovers correctly.
- **EXIF Sub-IFD Timestamp Reachability**: `ExifHandler.extract_timestamp` now reads the Exif sub-IFD (pointer tag `0x8769`) via `Image.Exif.get_ifd`, merging it with IFD0 before the priority walk. `DateTimeOriginal` (0x9003) and `DateTimeDigitized` (0x9004) live in the sub-IFD, which `Image.getexif()` does not expose at the top level, so every photo was previously named from IFD0 `DateTime` (file modification time) instead of capture time. The declared priority `DateTimeOriginal` > `DateTime` > `DateTimeDigitized` is now actually honored, and a malformed higher-priority tag falls through to the next candidate rather than aborting. Applies to HEIC as well, since pillow-heif exposes EXIF through the same API.
- **`batch_categorize` No Longer Returns Aliased Internal State (Issue #37)**: `FileCategorizer.batch_categorize` ended with `return self.categorized_files.copy()` — a shallow copy whose six list *values* were the exact list objects the categorizer keeps mutating. The very next call clears every one of those lists in place (`self.categorized_files[category].clear()`) before refilling them, so a caller holding a "snapshot" from a prior call watched it silently empty itself the moment `batch_categorize` ran again on the same instance, and — since the aliasing runs both directions — a caller mutating what it received back (appending to or clearing a returned list) corrupted the categorizer's own view of the run without raising anything. `batch_categorize` is called multiple times per run against the same `FileCategorizer` instance, and the only thing that kept this from being a live bug was the accidental ordering of those calls; reordering them (a natural side effect of restructuring the pipeline) would make sidecar deletion or the categorization summary silently see the wrong file list, misfiling or mis-deleting nothing the output would reveal, in a tool whose archive is the only surviving copy. `batch_categorize` now returns `{category: files.copy() for category, files in self.categorized_files.items()}` — a genuine per-category copy — so neither the returned dict nor any of its list values alias internal state; `get_files_by_category`, `get_sidecar_files`, and `get_processable_files` were already independent and are unchanged, and `FileProcessor._generate_summary`'s `processed_files`/`failed_files`/`quarantined_files`/`conversion_log` copies were already independent snapshots (their elements are appended to, never mutated in place), now pinned by new tests rather than left as an unverified assumption. Categorization results are correct regardless of the order `batch_categorize`, `get_categorization_stats`, and `get_file_summary` are called in, and the existing invariants that categorization runs exactly once per run (issue #13) and that unknown files are never dropped from `get_processable_files` (issue #29) are unchanged. New tests capture a `batch_categorize` result, run a second, unrelated `batch_categorize` on the same instance, and assert the first result's lists are untouched (this fails against the old shallow copy); mutate a returned dict and assert the categorizer's own stats are unaffected; and assert no per-category list in the returned dict is identical to the corresponding internal list.
- **A Reused `FileProcessor` No Longer Reports The Union Of Two Runs (Issue #35)**: `FileProcessor` held four mutable accumulators (`processed_files`, `used_timestamps`, `failed_files`, `conversion_log`) plus three more inside its collaborators (`ExifHandler.missing_exif_files`, `HeicConverter.converted_files`/`failed_conversions`, `FileCategorizer.categorized_files`), and `process_all_files` never reset any of them — it appended to them, then summarized `len(...)` of each. A second `process_all_files` call on the same instance therefore reported the *union* of both runs as if it were one: verified with two files in run 1 and two different files in run 2 on the same processor, run 2's summary read `files_processed=4` even though only two files moved that run. A public `clear_processing_state` already existed and a test already asserted it reset all seven containers completely, but nothing in production ever called it — the class advertised reuse while the implementation only supported single-use, a defect latent only because `main.py` constructs one `CLIInterface` and runs once, and certain to surface the moment anything loops (a per-month batch, a retry, a watch mode, or a test sharing a fixture) and misreport exactly the numbers a destructive tool's user relies on to know what happened to their only copy. `FileProcessor` is now explicitly reusable: `process_all_files` calls `clear_processing_state()` as its first statement, so every per-run accumulator — including each collaborator's own bookkeeping, not just this object's four — is reset before the run's first side effect, and a second call's summary describes that run alone. The alternative (making the object single-use and raising `RuntimeError` on a second call) was rejected: it forecloses the exact reuse the issue anticipates for no correctness benefit the reset does not already provide, and it would have meant deleting a public method a test already exercised rather than simply wiring it up — strictly more churn for a worse contract. The reset is deliberately selective about *what* it restores: the per-directory collision-name sets (`used_timestamps`, issues #6/#21) are cleared, not preserved, so the next file placed in a directory reseeds its claimed-names set from that directory's actual on-disk contents rather than a stale in-memory snapshot — correct, not an oversight, since a second run must see whatever this run (or a completely different process) has since written to `backup/`. The four accumulators are now private (`_processed_files`, `_used_timestamps`, `_failed_files`, `_conversion_log`), matching the `_`-prefix convention already used for `_scan_export_directory`/`_process_single_file`, with `_generate_summary` their only reader; `quarantined_files` (issue #58) is the same kind of per-run bookkeeping and is renamed `_quarantined_files` alongside them for a consistent public surface (its reset behavior was already correct and is unchanged — naming only). A second, related defect is fixed alongside: `missing_exif_list` used to carry the *source* path recorded at EXIF-extraction time, which by the time `display_missing_exif_warning` renders the summary has already been moved, renamed, or deleted by a real run — the panel told a user to "consider manually reviewing" paths that no longer existed anywhere on disk, verified end to end (four reported paths, all four `False` on an existence check). Each `missing_exif_list` entry now carries both the file's final `backup/` location (where a real run actually put it) and its original `export/` name, shown parenthetically for identification (`backup/photos/2024.01.15.14.30.45.jpg  (was export/IMG_1234.jpg)`); a dry run, which moves nothing, instead reports the still-existing original path with no final path, since none was created. This also changes *what* `missing_exif_files`/`missing_exif_list` count, deliberately: they used to count every file whose EXIF extraction failed (`ExifHandler.missing_exif_files`), regardless of what happened to it afterward, but now count only files that actually landed using a fallback timestamp — a file that lacks EXIF and then fails to move is counted in `files_failed` instead, never in `missing_exif_files`, since it was never "processed using filesystem timestamps" as the warning panel claims and reporting it in both places would double-count one failure as two different outcomes; this is pinned by a dedicated test. New tests drive two full real runs on one `FileProcessor` instance with genuinely distinct files and assert the second summary's counts and `processed_files` list name only the second run's work (failing against the old code, which reported the union); a same-instance run 2 that collides with a file already sitting in `backup/photos/` — placed there independently of this instance, standing in for a separate process — is bumped to the next second rather than overwriting it, with a spy on the `O_CREAT | O_EXCL` reservation call confirming the collision is never even attempted (the re-seed already knew), not merely recovered from after a failed attempt; and a missing-EXIF entry's reported path actually exists on disk both after a real run (the final path) and during a dry run (the original path), where the old string-only shape errors outright. Every invariant `process_all_files` and its collaborators already enforced is unchanged: atomic `O_CREAT | O_EXCL` collision reservation (#6), per-category collision namespaces (#21), the `files_processed + files_failed == files_seen` accounting and 0/1/2/130 exit-code taxonomy (#31), and the single-public-entry-point layering rule that `CLIInterface` calls no `_`-prefixed member of `FileProcessor` or its collaborators (#13).
- **Directory-Check And Top-Level Failures No Longer Mask Their Real Cause Or Discard Their Traceback (Issue #39)**: Three cross-cutting error-handling gaps let real, diagnosable failures either produce no output at the default log level or lose the information needed to act on them. `CLIInterface.check_directories`'s `any(export_path.iterdir())` call had no guard of its own, so a directory that exists but cannot be listed (e.g. a permissions problem on a mounted drive) raised a raw `PermissionError` straight past this method to `main.py`, while three lines below it the `backup_path.mkdir(...)` call *was* guarded — but with a bare `except Exception`, which additionally swallowed a `TypeError`/`AttributeError` from a malformed `--backup-dir` value and reported it as "cannot create backup directory," a description that does not match what actually happened. The `iterdir()` call is now wrapped and reported the same way the `mkdir` call already was, and the `mkdir` catch is narrowed to `OSError` — its actual subclasses (`PermissionError`, `FileExistsError`, `NotADirectoryError`, disk-full) are still caught and reported; anything else now propagates with its real type. Separately, `main.py`'s top-level `except Exception` printed a one-line message and only appended `traceback.format_exc()` when `--verbose` happened to be passed — by the time a user without `--verbose` realizes they need the traceback, the only way to recover it is to reproduce the failure. It now also calls `logger.exception(...)`, which records the traceback at `ERROR` unconditionally, routed through the logger (not a second `console.print`) so it passes through the same `_SanitizingLogFilter` boundary issue #9 established rather than bypassing it. That filter, in turn, only ever rewrote `record.msg`/`record.args` — the formatted traceback text (`record.exc_text`, built from `record.exc_info`) is appended by the standard `Formatter` *after* filters run, so an untrusted value embedded in an unexpected exception's own `str()` was never sanitized the way the same value already is in an ordinary log message. The filter now also pre-computes and sanitizes `record.exc_text` when `record.exc_info` is present, closing that gap at the same single boundary; `markup=False` and the rest of the filter's behavior are unchanged. Finally, `FileProcessor._failed_files` stored `str(exc)` at every one of its five append sites (`_delete_sidecar_files`, `_process_category`, `_process_single_file`'s move and HEIC-verify branches, `_process_unknown_file`, `_quarantine_file`), discarding the exception's type before the failure ever reached the results table — the Error column showed `[Errno 2] No such file or directory: '...'` with no indication of which exception class produced it. Each site now stores the caught exception object itself; `CLIInterface.display_failures` renders it as `f"{type(error).__name__}: {error}"`, falling back to the plain string for the handful of failure reasons (e.g. `'HEIC conversion failed'`) that were never a caught exception in the first place. `_process_category`'s own broad `except Exception` — the one place in the pipeline a bad file must not abort the whole batch — is left exactly as it was and now carries a comment stating why it is the sanctioned exception to the narrow-except rule the rest of this fix applies. One catch this issue's own investigation ruled out despite matching its title: elevating `FileCategorizer._read_image_metadata`'s DEBUG-level open-failure log to WARNING would have re-flagged, on every run, every RAW file (`.dng`/`.cr2`/`.nef`/...) a user has — Pillow has no codec for RAW at all, so that open failure is the expected, universal case for a perfectly good photo, not a diagnosable problem — while adding nothing for the extensions where "unopenable" IS a real failure, since issue #58's `_is_decodable_image` already independently re-checks and WARNs on exactly those before a file is ever filed, correctly routing it to `backup/corrupt/` instead of `backup/photos/`. That log site keeps its DEBUG level and gains only a narrower `except` clause (dropping the bare `except Exception`, which also silently discarded bugs like a test double's own `AssertionError`) and the exception's type in its message for anyone running with `--verbose`. Every accounting invariant is unchanged: the exit-code taxonomy (#31), the `files_processed + files_failed == files_seen` partition, verify-before-delete (#7), and the quarantine/routing decisions issues #54/#56/#58/#63 established are untouched by this fix — only what gets logged, at what level, and what a caught exception retains through to display.
- **Sidecar Deletion Now Validates Content, Is Conditioned On The Run Actually Archiving Something, And Is Reported (Issue #57)**: `_delete_sidecar_files` was the very first thing `process_all_files` did, and unlinked every match unconditionally — membership in `FileCategory.SIDECAR` is decided purely by the `.aae`/`.AAE` extension, so any file that merely shared it, of any size or content, anywhere in the export tree, was destroyed on the first run with no content check, no pre-deletion listing, and no mention in the results table. The issue's own reproduction destroyed a 23-byte `tax-return-2024.AAE` of unrelated user data while the banner read "Success!". Two further defects compounded this: a genuine sidecar carries the user's non-destructive edit history (crops, filters, markup) and was deleted before a single photo had actually landed in `backup/`, so a run that failed midway lost the edits *and* left the photos unprocessed; and the deletion never appeared anywhere a user would see it. A candidate is now unlinked only once its content is confirmed to actually be a property list: a new `_looks_like_apple_sidecar` reads the leading 16 bytes and checks them against `SIDECAR_MAGIC` (`<?xml` for an XML plist, `bplist00` for a binary one), returning one of three states rather than a plain boolean — matched, read-but-not-matched, or could-not-be-read-at-all (a permission error, a directory literally named `dir.aae`, or a scan/delete race) — so a perfectly good sidecar hit by a permissions error is never told it "was not a plist," a claim about content nobody actually inspected; the read failure fails closed by construction either way, never treating an unreadable file as validated. The delete call itself moves from the top of `process_all_files` to after the per-category processing loop, so nothing is deleted until every processable file has been filed in `backup/` or recorded as failed — but completing that loop is not by itself proof anything landed: `_process_category`'s own per-file catch-all (issue #39) guarantees the loop completes even when every single processable file failed, a full disk partway through a real run being the ordinary way that happens, so the deferred call is now additionally gated on the run having actually archived something. That gate is computed as attempted-file-count minus `_failed_files`, never by reading `_processed_files` directly, because a dry run's planning branch never appends there at all — reading it directly would make every dry run look like "nothing archived" and break dry-run/real-run parity; a quarantined file (issue #58) still counts as archived either way, since its bytes did land safely in `backup/corrupt/`. When the gate trips, every sidecar candidate for that run is kept under a fourth reason, `'run_archived_nothing'`, without being individually re-validated. Two new per-run accumulators, `_deleted_sidecars` and `_skipped_sidecars`, are reset in `clear_processing_state` alongside the existing six (issue #35's contract, now directly pinned by tests that fail if either `.clear()` call is dropped), and feed two new summary keys — `sidecars_deleted` and `sidecars_skipped` — plus a `skipped_sidecar_files` list of `(reason, path)` pairs naming why each candidate survived (`'not_plist'`, `'unreadable'`, `'delete_failed'`, or `'run_archived_nothing'`). `CLIInterface.display_results` renders an unconditional "Sidecar Files Deleted" row, present in both dry-run and real-run output, and — when at least one candidate was kept for any reason — both a "Sidecars Kept" banner (rather than an unqualified "Success!", closing the gap where a genuine `os.remove` failure or an unarchived run previously surfaced no differently than a clean run) and a conditional detail table naming each one, with every filename passed through the existing `safe_markup`/`sanitize_for_display` escaping (issue #9) before it reaches a rendered table. Neither a validated deletion nor any kept candidate is counted in `files_processed` or `files_failed`: a sidecar was never a processable file to begin with (issue #31), so `files_processed + files_failed == files_seen` is unaffected either way — this was a deliberate departure from the issue's own sketch, which would have folded a delete failure back into `_failed_files`. A dry run validates content exactly as a real run does but performs zero `os.remove` calls, and is asserted directly to report the identical `sidecars_deleted` count a real run over the same input reports (issue #10 parity), including when the archived-nothing gate is not in play. The project owner declined the `--keep-sidecars` escape hatch the issue itself considered adding: validating, deferring, gating, and reporting is the whole fix, for the same reason `--keep-heic` was removed rather than fixed in place (issue #65) — a flag a user does not need is maintenance surface, not safety.
- **Hidden Files Are Now Counted Instead Of Vanishing From Every Total (Issue #30)**: `_scan_export_directory` dropped any file whose basename started with a dot before it ever entered `all_files`, so a hidden file was absent from `batch_categorize`, `get_categorization_stats()['total']`, `failed_files`, and `missing_exif_list` alike — there was no number anywhere in the results dict from which a user could infer that anything had been skipped, and a `.hidden_photo.jpg` with perfectly valid EXIF was silently left behind while the run exited `0` and printed "All files processed successfully!" The rule was also inconsistent across levels: `os.walk` still descended into dotted *directories* (issue #56 fixed that separately), so the exact same leading dot meant "processed" one level down and "dropped" at the top. The scan now distinguishes genuine OS junk from everything else: a new `HIDDEN_FILE_DENYLIST` (`.DS_Store`, `.localized`, `Thumbs.db`) matches by exact basename rather than folding junk into the blanket dot-prefix rule, so the intent is legible — these specific names are always correctly ignored, not "anything hidden happens to be junk." Every dotted file, denylisted or not, is still excluded from processing (matching the already-fixed hidden-*directory* policy at the file level, so the inconsistency issue #56 left standing is closed too), but is no longer dropped silently: it is recorded in a new `_skipped_files` accumulator as `(reason, path)` (`'junk'` or `'hidden'`), surfaced as a `files_skipped` count and a `skipped_files` list, and rendered as its own "Files Skipped" table row and detail table by `CLIInterface.display_skipped_files` — deliberately a separate mechanism from issue #57's `_skipped_sidecars`/"Sidecar Files Kept", since a skipped file never even reached the categorizer (excluded at the scan boundary, by name) while a kept sidecar was categorized and reached, then failed, delete validation; the two answer different questions about different pipeline stages, so they stay two accumulators and two rows rather than one row that would blur which explanation applies. They are added together only where they must agree: a new `files_scanned` key (categorization total plus skipped) makes the accounting invariant this issue shares with #29 concrete and testable — `files_scanned == (files_processed + files_quarantined) + sidecars_deleted + (files_skipped + sidecars_skipped) + files_failed` — asserted directly in a new test after a non-dry run mixing every outcome (processed, quarantined, HEIC-failed, sidecar-deleted, sidecar-kept, hidden-skipped, junk-skipped). Withholding the unqualified "Success!" banner is deliberately narrower than "any skip at all": a junk-only skip (`.DS_Store`/`.localized`/`Thumbs.db`) does **not** demote it, because essentially every macOS export tree carries a `.DS_Store` — if that alone withheld the headline, it would never read "Success!" in ordinary use and the signal would carry no information, the same reasoning issue #39 already applied (a routine RAW-open failure stays at DEBUG, not WARNING, because it would otherwise fire on every valid RAW on every run) and the reasoning that made issue #57's own demotion acceptable (a user's real sidecars are all valid, so it cannot fire spuriously for them). Only an *unexpected* skip — a dotted name that did not match the denylist, meaning a real file the tool declined to handle — withholds it, which is the correct reading of this issue's own acceptance criterion 5 ("a user must never be told... while **a photo** remains in `export/`," not while a `.DS_Store` does); the junk-only skip is still fully counted and named in the results row and detail table, since the counting half of this fix is unconditional. The decision of whether a run "looks clean" now lives in exactly one place, a new `is_unqualified_success(results)` function in `src/cli_interface.py` that both `display_results` (for its title) and `main.py` (for its standalone "All files processed successfully!" line) consult, rather than each independently recomputing an answer that could drift; `main.py` previously duplicated this logic locally, incorrectly folding in `files_quarantined` under this issue's own justification even though a quarantined file has already moved to `backup/corrupt/` and so never meets acceptance criterion 5's "remains in `export/`" condition at all — it is `is_unqualified_success` withholding the banner for quarantine that is correct, for issue #58's own reasons, not this issue's. A skipped file does not change the exit code: like quarantine and kept-sidecars, it is a deliberate, handled outcome rather than a tool failure, so `0`/`1`/`2`/`130` keep their exact existing meanings (issue #31) and no two codes collapse into each other. `_skipped_files` is reset in `clear_processing_state` alongside the existing seven accumulators, pinned by extending the two existing tests that already enumerate that container-by-container reset (issue #35's contract) rather than adding a parallel one. Dotted-directory pruning (issue #56) is untouched — it was already correct and is verified, not re-implemented, by this issue's own test suite.
- **Implausible Timestamps No Longer Name An Archive Path (Issue #62)**: Every timestamp source in `exif_handler.py` accepted any value its own parser would take, with no check that the result was a plausible capture time — an EXIF `DateTime` of `9999:12:31 23:59:59` or `0001:01:01 00:00:00` named a file `9999.12.31.23.59.59.jpg`, and a zeroed QuickTime `mvhd` box (the container format's own epoch sentinel, 1904-01-01, common in files stripped by re-muxers and messaging apps) named a video `1904.01.01.00.00.00.mp4`. This was not hypothetical: running the tool over the project owner's real export produced exactly that for two AI-generated mp4s with no Apple metadata and a zeroed `mvhd` — `backup/videos/1904.01.01.00.00.00.mp4` and `…00.01.mp4`, the second bumped a second forward by the existing collision logic, making two unrelated files look like a burst pair shot in 1904 — with the original filenames destroyed by the rename and no way to recover them. The fix uses two deliberately separate mechanisms rather than one collapsed check, after a first pass at conflating them proved actively harmful. A generic plausibility predicate, `ExifHandler._is_plausible_capture_time`, bounds every source that can produce a candidate timestamp to `[1826-01-01, now + 1 day]` — 1826 being the earliest surviving photograph, chosen deliberately generous because a scanned family photograph carrying a genuinely backdated 1950s/60s `DateTimeOriginal` is a legitimate, valued input to a personal archive, not noise to be filtered; the upper bound allows one day past `datetime.now()` (an injectable parameter, defaulting to the live clock, so both bounds are pinned deterministically in tests) so a capture made across a timezone boundary is accepted rather than treated as hostile. This predicate is applied at EXIF (`_parse_exif_datetime`), Apple's local-time key (`_extract_quicktime_creationdate`, issue #28), hachoir's `mvhd` reading and its `exportPlaintext` last resort (`_extract_video_timestamp_hachoir`), and issue #51's filename-fallback patterns (`_extract_timestamp_from_filename`), whose bare four-digit year fields were found to admit the identical 0000–9999 range as the crafted-EXIF case. Critically, this floor does *not* catch the QuickTime epoch: 1904 is *later* than 1826, so it passes the generic check untouched, on purpose — 1904-01-01 is not "implausibly old" in the general sense that predicate polices, it is a sentinel meaning `mvhd` never recorded a value at all. That sentinel is now rejected by a second, dedicated check, `ExifHandler._is_quicktime_epoch_sentinel`, scoped to the `mvhd`-derived reading alone and covering the whole 1904-01-01 calendar date (not just the exact zero instant), since the real reproduction's second file landed one second past the epoch after an independent zero was bumped by the collision logic. An earlier attempt at this fix raised the generic floor to the Unix epoch (1970) to catch 1904 with one check instead of two — which happened to satisfy the video acceptance criterion but silently reintroduced the opposite failure, rejecting every legitimately backdated scanned-photo date as collateral damage; keeping the two concerns apart avoids that trade entirely. Every rejection, from either mechanism, falls through exactly as a missing value already did — never raising, never clamping — so a file with an implausible or sentinel source still gets archived under a filesystem timestamp instead of being abandoned; a crafted higher-priority EXIF tag still falls through to a valid lower-priority one, and a crafted Apple `creationdate` still falls through to a plausible `mvhd` reading. The pre-existing malformed-string rejections (empty, NUL-padded, a 4000-character value, an embedded ANSI escape, a non-`str` value, a negative year) were already non-raising and remain so, now pinned as explicit regression tests rather than resting on ad hoc verification.
- **Screenshot-Vs-AI-Content Detection Precedence Made Explicit (Issue #22)**: `FileCategorizer.categorize_file` checked the screenshot filename pattern before ever consulting AI/C2PA provenance for a `.png`: `_is_likely_screenshot(filename)` returned `FileCategory.SCREENSHOT` immediately on a match, so `_is_generated_content` never ran at all for any PNG whose name happened to look like a screenshot. A PNG carrying a genuine `Software: ChatGPT / OpenAI DALL-E` marker and named `Screenshot 2024-01-15.png` was filed as a screenshot with the AI provenance detected but silently ignored — reachable in practice by screenshotting a generated image, or saving one through a tool that applies screenshot-style naming. ### Security
- **Dependency Floors Raised Past Known-Vulnerable Releases, And A Hash-Pinned Lockfile Added (Issue #59)**: every file in `export/` is handed to Pillow, `pillow-heif` (libheif), and `hachoir` for decoding — all three parse untrusted binary data, and the first two are C-backed with active CVE histories — yet `pillow>=10.0.0` (the previous floor) was satisfied by Pillow 10.0.0 itself, a release directly vulnerable on paths this tool exercises: CVE-2023-4863, a heap buffer overflow in the libwebp Pillow bundles at the time, reachable through any `.webp` in `export/` since `.webp` is in `PHOTO_EXTENSIONS`, fixed only in 10.0.1; CVE-2023-44271, an `ImageFont`/`textlength` memory-exhaustion DoS, also fixed in 10.0.1; and CVE-2024-28219, an unsafe-`strcpy` buffer overflow in `_imagingcms.c`, fixed only in 10.3.0 — all three verified directly against NVD/vendor advisories rather than taken on the issue's word. `pillow`'s floor is now `>=10.3.0,<13` (the ceiling also widened from `<12`, since Pillow 12.x — already the version installed and exercised by this project's own test suite — shares the EXIF API this tool relies on). `pillow-heif`'s floor moves to `>=0.16.0,<2`: 0.16.0 is the first release requiring `libheif>=1.19.0`, well past the libheif versions carrying CVE-2023-0996 (a strided-image buffer overflow) and CVE-2024-41311 (an `ImageOverlay::parse` out-of-bounds read/write, `libheif<=1.17.6`) — both reachable since every `.heic` in `export/` is decoded through this library. `click`, `python-dateutil`, `rich`, and `hachoir` also move to `>=8.1.7`, `>=2.8.2`, `>=13.7.0`, and `>=3.3.0` respectively (ceilings widened to match, `rich`'s to `<16`) — none tied to a specific named CVE for this tool's own usage, so each is documented in `pyproject.toml`'s own comment as matching or exceeding the version this project's test suite has already verified safe, not as a security fix in its own right; inventing a CVE justification where none exists would be worse than being explicit that there isn't one. A new hash-pinned `requirements.lock`, generated with `pip-compile --generate-hashes` against `pyproject.toml` (in a disposable venv, never `tm-backup-env` itself, so the project's own dev environment is untouched) and verified end to end with a real `pip install --require-hashes -r requirements.lock` in that same disposable venv before being committed, pins every direct and transitive dependency to one exact, hash-verified version, so an install is reproducible and tamper-evident rather than whatever a resolver happens to pick from an index snapshot, a mirror, or an offline wheelhouse on a given day. `README.md` gains a new `## Security` section stating the untrusted-input threat model directly (every file in `export/` reaches a C-backed decoder with an active CVE history) and the dependency-currency expectation that follows from it, plus the `pip install --require-hashes -r requirements.lock` install command and the regeneration command for after a future `pyproject.toml` change. New tests (`tests/test_dependency_pins.py`) parse `pyproject.toml` directly (via regex, not a TOML library, since this project's Python 3.9 floor predates `tomllib`) and assert every floor meets or exceeds the issue's named minimum, that `requirements.txt` mirrors `pyproject.toml` exactly, that the lockfile exists and documents `--require-hashes`, and that every direct dependency's lockfile pin falls within `pyproject.toml`'s own declared range — confirmed to fail against the pre-fix `pyproject.toml` and the missing lockfile by stashing those changes and rerunning. The issue's remaining item, wiring a `pip-audit` run into CI, is **deferred to issue #17, not met** (the controller's explicit ruling on this acceptance criterion, fix-round-1): this project has no CI pipeline at all, and the issue's own dependency list names CI as where the audit runs, so there is nowhere for that step to run until #17 exists; the floors and the lockfile — the substantive half — are done regardless.

- **Tests Weaker Than They Look, Strengthened Or Annotated (Issue #68)**: residue from milestone 1.2.0's fifteen reviews, carrying no defect. A test that passes for the wrong reason advertises coverage that is not there. Strengthened: the categorize-once tests patched at *instance* level, so a regression categorizing through a newly constructed `FileCategorizer` went uncounted -- exactly the shape a second pass would take (demonstrated: instance-level counts 1 of 2 calls, class-level with `autospec` counts 2 of 2); an abort test's 0-byte `.aae` had become decorative since #57 made content validation the gate, so its on-disk assertion would have passed even if the deletion ran; a no-decode trap raised `AssertionError`, which the code's broad `except Exception` swallowed, turning "a decode happened" into a vague "result was None"; and a `== 2` decode count on deliberately-deferred Pillow behavior would have turned the eventual fix into a red test blaming the counting mechanism. - **Interruption And Partial-Failure Behavior Pinned (Issue #46)**: `FileProcessor` deletes originals, so how a run behaves when it is cut short is as load-bearing as the happy path — yet the most important piece was unasserted. `_process_category` catches `except Exception`, and because `KeyboardInterrupt` is a `BaseException` (not an `Exception`), a Ctrl-C raised mid-batch escapes the per-file loop and unwinds the run instead of being swallowed into a per-file skip that would grind through the entire library while the user holds the key. A new `tests/test_interruption.py` pins that contract: a `KeyboardInterrupt` on the third file propagates out of `process_all_files` (`assertRaises`), the two files processed before it already landed in `backup/`, the remaining three are untouched in `export/`, and the interrupt is never demoted to a recorded failure — a test that fails the instant that `except Exception` is "cleaned up" to a bare `except:`/`except BaseException`. The module also pins two previously unasserted partial-failure behaviors: a full disk (`OSError(ENOSPC)`) does not abort the batch — every remaining file is still attempted and recorded as a `move_file` failure while the run completes — and a file deleted between the scan and processing is absorbed by `batch_categorize` so the run finishes over the survivors without crashing. Scenarios already covered elsewhere (one-file `PermissionError` partial failure, `clear_processing_state` fully resetting, and the top-level `main.py` `KeyboardInterrupt` handling) are deliberately not duplicated.
- **Regression Coverage Locking In The Single-Categorization-Pass Guarantee (Issue #11)**: Issue #11 reported every file categorized three times per run — `FileCategorizer.categorize_file` (and its `_is_generated_content` PNG/EXIF probe, which opens the image with Pillow) ran once from `CLIInterface.display_file_scan_results` to render the discovery table, once from `process_with_progress` to get the sidecar list, and once more from `FileProcessor.process_all_files`, the pass that actually mattered. Investigating found that improvement already shipped, by the two `### Changed` entries above: issue #13's single-entry-point refactor and issue #14's `ProgressReporter` seam replaced "CLI categorizes once and hands the result down to `FileProcessor`" with the inverse — `FileProcessor` performs the one categorization pass itself and reports the resulting stats *up* to `CLIInterface.display_categorization_summary` through `on_categorized` — so `process_with_progress` no longer touches the categorizer at all (that call site is gone outright) and the discovery table, sidecar deletion, and file processing all read from the one pass `process_all_files` still performs. `display_file_scan_results` (the original first call site) still exists and still calls `batch_categorize` on its own, but `process_with_progress` no longer calls it — it renders the table via `display_categorization_summary` instead — so it is dead code, unreachable from a real run, exercised only by tests that call it directly and in isolation; it was left as-is rather than rewired, since changing unreachable code carries the risk of the change without any of the benefit. This entry records verification of that already-shipped fix, not a second delivery of it. Confirmed with real numbers, not projections: instrumenting a real 60-file, real-photo-resolution run through the actual `CLIInterface.process_with_progress` entry point (the same one `src.main` calls) shows `batch_categorize` running exactly once and `categorize_file`/`_is_generated_content` running exactly once per file today; checking out the commit immediately before issue #13 and profiling the identical batch with `cProfile` reproduces the historical "before" state this issue described — `batch_categorize` x3, `categorize_file` 180 calls, `_is_generated_content` 150 calls, 0.026s cumulative — against the current `batch_categorize` x1, `categorize_file` 60 calls, `_is_generated_content` 50 calls, 0.007s cumulative: exactly the 3x-in-calls, ~3.7x-in-cumtime reduction the issue predicted for this probe, though because `Image.open` here is a lazy header/EXIF read rather than a forced full decode, the effect on total run time at this batch size is small (under 1%) — the win scales with batch size and HEIC share rather than mattering much for 60 files. Four new tests (`tests/test_categorize_once.py`) instrument `_is_generated_content` and `categorize_file` directly on the categorizer instance a real `CLIInterface.process_with_progress` run drives, and assert every scanned file is categorized exactly once; each was confirmed to fail (3 calls per file) against the genuinely pre-#13 code and pass against the current code, so they lock in the reduction against a future regression even though no production code changed to satisfy them here. Issue #13's layering invariant (`CLIInterface` calls no `_`-prefixed member of `FileProcessor` or its collaborators) and issue #37's non-aliased `batch_categorize` return value are unaffected; the further win the issue notes but explicitly defers — collapsing `_is_generated_content`'s and `ExifHandler.extract_timestamp`'s independent per-file metadata reads into one — remains open for a future issue.
- **`tests/run_tests.py` Now Reports Every Mode It Runs, And Runs Every Test It Claims To (Issue #50)**: The custom runner's `--unit-only` branch built its own `TestResult` and called `sys.exit()` before the shared TEST SUMMARY block, so the one thing a custom runner exists to add over plain `unittest discover` — a reported pass/fail count — was unreachable under that flag; a run could fail silently while printing nothing about what failed.
